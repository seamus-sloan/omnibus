# Architecture

Cargo workspace with five crates:

- **`shared/`** (`omnibus-shared`) — serde types shared across every target (`Settings`, `ValueResponse`, `LibraryContents`, `LibrarySection`). No Dioxus / axum / sqlx deps.
- **`db/`** (`omnibus-db`) — server-side data layer: SQL migrations, SQLite pool init, the normalized query layer, and the indexing pipeline (scanner → ebook metadata extraction → atomic per-library upsert). Consumed by both `server/` (REST handlers) and `frontend/` (server-function bodies). Holds all sqlx / tokio / epub / anyhow dependencies on the server side.
- **`frontend/`** (`omnibus-frontend`) — Dioxus UI + server-function wire layer (`rpc/`, split into per-domain submodules re-exported from `rpc/mod.rs`). Feature-gated:
  - `web` — WASM client build (used by `server/` when `dx serve --platform web` builds it for WASM).
  - `mobile` — Native Dioxus build; uses `reqwest` against `/api/*` REST routes.
  - `server` — SSR/native build; pulls in `omnibus-db` and compiles server-function bodies. Name is hardcoded by the dioxus_fullstack_macro — can't be renamed.
- **`server/`** (`omnibus`) — **unified Dioxus fullstack binary**. Built twice by `dx serve`: once native (feature `server`) for the axum backend + SSR, once WASM (feature `web`) for the hydrated client. Hosts the hand-written `/api/*` REST router for mobile. Depends directly on `omnibus-db`.
- **`mobile/`** (`omnibus-mobile`) — thin Dioxus Native shell that seeds the reactive `ServerUrl` context from `data::server_url_store` and launches `omnibus_frontend::App`. Android-only: nothing builds this crate for iOS anymore — the iOS surface is the native `omnibus-ios/` app below.

Default `cargo build` / `clippy` covers `server`, `shared`, `frontend` only. Mobile is excluded via workspace `default-members` because its `mobile` feature is mutually exclusive with `web`; build it explicitly: `cargo build -p omnibus-mobile`.

**Web request flow (fullstack):** browser → axum serves SSR'd HTML + WASM bundle → hydration → signal effects call Dioxus server functions (`#[get]`/`#[post]` in `frontend/src/rpc/`) at `/api/rpc/*` → same handlers execute server-side against the SQLite pool via an `axum::Extension<SqlitePool>` layer.

**Mobile data flow:** Dioxus signal/effect → `reqwest` call to `/api/*` (hand-written handlers in `server/src/backend.rs`) → signal update → re-render. Mobile deliberately does **not** use the `/api/rpc/*` server functions. Every mobile read is cache-first (stale-while-revalidate): the local copy is served instantly, a background revalidation refreshes it and nudges rendered pages via a generation channel, and known-offline reads never touch the network. User writes queue to a durable outbox on connectivity failure, and a periodic background tick keeps the outbox drained and the library replica fresh — see `frontend/src/offline.rs` below.

**Database:** schema ships as numbered SQL migrations under [db/migrations/](../db/migrations/), embedded via `sqlx::migrate!` and run on pool init in `omnibus_db::init_db`. Applied versions are recorded in the `_sqlx_migrations` table. Add new migrations as `NNNN_description.sql` — never edit an applied file. All tests use `sqlite::memory:` for isolation; the migrator runs against them the same as production.

**Server URL (mobile):** the backend base URL is a reactive `ServerUrl(Signal<String>)` context, seeded at launch from `data::server_url_store` (persisted at `<data_dir>/server` — `Library/Application Support/omnibus/server` on iOS, `$HOME/.omnibus/server` on desktop/dev, `Context.getFilesDir()/server` on Android — plaintext, all builds; the URL isn't secret). Empty on first run → the mobile `ScreenLayout` gate routes to the unguarded `/connect` route (`pages/server_connect.rs`), which validates reachability via `data::check_server` (`GET /api/_health`) before persisting and advancing to `/login`. The login screen shows a connected-to bar with a Back button to change it. `use_server_url()` still returns a `String` snapshot, so all readers are unchanged; `use_server_url_signal()` is the writer accessor.

Each `DetectedSuggestion` carries a `Tier` (Zero = high-confidence normalized-key/regex match, One = fuzzy match; both always surfaced, no opt-in gate), a `score` (1.0 at Tier 0; at Tier 1 the fuzzy Jaccard similarity for merges, else a fixed 0.75 for tag-split/book-title), and a `CleanupPayload` (Merge/Split/Rename/Delete) — enough to persist as a `dedup_suggestions` row (migration 0069). `CleanupError`. interaction.rs      — the one SQL expression behind the "Recently Interacted" sort axis: the most recent moment *anyone* touched a book, folded from `books.last_modified`/`timestamp` plus correlated `MAX`es over `user_ratings`, published `journal_entries`, `book_read_status`, and `physical_copies`. Exposed as a macro (so the `const BOOK_COLUMNS` projection can `concat!` it) with `INTERACTED_AT_EPOCH`/`INTERACTED_AT_ISO` runtime handles for `format!`-built queries; `page` orders on the ISO form (its cursor compares text), smart shelves on the raw integer. **Derived, never stored** — the same argument rule 09 makes for content validators: a `books.last_interacted_at` column would need bumping at seven write sites and would drift the first time one was missed. Metadata edits and cover replacements need no join of their own, since both already land on `books.last_modified` via `touch_book_last_modified`. Journal *drafts* are excluded on purpose — a private draft must not reveal itself by moving a book up a shared sort. Projected onto every listing (not just this axis) because the landing re-sorts each fetched page client-side and a missing key would collapse to the id tiebreak. tests.rs sibling.
```
metadata_lookup/    — server-side book-metadata resolution for scans that miss the library (F Physical Check-In). Two entry points, one per question a caller can ask: `search_provider_by_isbn` and `search_provider_by_title` — neither names a provider, so callers never learn which are configured. `config.rs` holds `MetadataLookupConfig` (injectable per-provider base URLs) + `ProviderKeys` (resolved settings-over-env by `settings::provider_keys`; a `None` key means that provider is skipped, not failed). `providers/` is one module per provider — `openlibrary.rs`, `googlebooks.rs`, `hardcover.rs` — each implementing the **same trio** (`by_isbn` → `Option<ProviderEdition>`, a text/structured search → `Vec<_>`, and `by_ref` → `Option<_>` for re-fetching one candidate by the handle its search handed out; a clean miss is an empty answer, an `Err` means the provider couldn't be asked), plus `http.rs` (shared client, `strip_url` so a request URL never reaches a log, year trimming, and the two value normalizers every provider shares — `sanitize_genres` and `paired_isbn10`) and `mod.rs` (`run` — the single dispatch — `by_ref`, `run_with_fallbacks`, and `ladder`). **Google's API key travels as an `X-goog-api-key` header, never in a URL** (#2131) — a `reqwest::Error` renders the request URL in its `Display` but never a header, so no fallible step in `googlebooks.rs` has a credential to write into `omnibus.log`, including ones added later; `strip_url` was the guard before that, and being opt-in per call site is exactly how it came to be missing from all three `json()` sites (#2129). **This is the path the leak actually fired on**, and the pairing is why: an unstripped decode error met a sink that walks the cause chain — `{e:#}` at `mod.rs`'s per-rung warn, `search.rs`'s fan-out warn, and `googlebooks.rs`'s swallowed bare-text fallback. A `%e` sink (what `book_summary` has) renders the outer context alone and would have hidden it. `no_google_books_url_carries_the_api_key` asserts the property over every builder rather than trusting each site. Providers are asked in **their own terms**, from a structured `query.rs::SearchQuery { title, author, isbn13 }` rather than one flattened phrase: Open Library gets a fielded `title=`/`author=` pair (handed the concatenation it searches the author's name *inside the title field*, which for "Dune Frank Herbert" returns five books written **about** Dune and not the novel — verified against the live API), Google Books keeps a bare-text `q` (its general search ranks the phrase as well as `intitle:`/`inauthor:` and tolerates typos far better), and an ISBN on the query routes every provider to its exact-identifier lookup. `run_with_fallbacks` widens a query that found nothing — as given, then without the ISBN, then without the author — scoring each rung against *that rung's* query. `relevance.rs` scores and filters what a provider returns (ported from BookOrbit's `candidate-relevance.ts`/`title-match.ts`): NFKD-fold → strip nonspacing marks → lowercase → letters/digits/spacing-marks, then a five-tier title match (exact 10 / whole-word prefix 8 / whole-word containment 7 / token overlap ×6 gated on a **strict** ratio > 0.5 / Levenshtein ×4 gated on similarity **≥** 0.6 — the asymmetry is load-bearing), an author bonus that only applies once the title already scored, an exact-ISBN short-circuit at 100, a floor of 3, a stable descending sort, and a skip-list that **drops** study guides and summaries rather than ranking them lower. Two deliberate divergences from the source, both documented in-module: spacing combining marks are kept (so Devanagari and friends aren't shattered at their vowel signs), and edit distance is counted in `char`s rather than UTF-16 code units. `throttle.rs`'s `ThrottleTracker` remembers a provider's 429 across requests — an escalating per-provider cooldown (Google Books gets its own longer schedule, its quota being daily rather than per-minute), honouring `Retry-After` when sent, reset by a *successful* call — one that recorded no refusal of its own, since a provider client can swallow its own failure and still answer `Ok` — while a lapse only ends the wait and deliberately keeps the escalation level, or the multi-step schedules could never advance past their first step. It lives on `MetadataLookupConfig` rather than the server's `AppState` because the REST handler and the web server function build their configs independently and neither can see the other's router state; `ThrottleTracker::shared()` is the process-wide instance, `fresh()` the isolated one every test uses. `ladder` orders the rungs: the two catalogs first, key-dependent (Google Books leads when keyed, since keyless it shares an anonymous quota it exhausts; Open Library otherwise), then **Hardcover last and only when keyed** — it costs an extra round trip, but it's the one provider carrying a series statement natively. Exactly one rung is **terminal** (the last catalog): if nothing hit and that rung failed, we never got an answer, so its error surfaces as `MetadataLookupError::Provider` rather than a "not found" we can't stand behind; every other rung — Hardcover included — is best-effort. `openlibrary::enrich` is the side lookup that fills `series`/`first_publish_year` (the edition record + the search API's `isbn:` query), joined concurrently with the ISBN ladder so a hit pays no extra latency; it never fails, and callers must hand it a **canonicalized** ISBN since it interpolates into a URL path. Normalization comes from `omnibus_shared::isbn`, shared with the check-in scanner so both ends gate on the same rule. `metadata_lookup/providers/`'s `catalog` (#1983) is the read-only capability catalog alongside the ladder: per-provider identity/`configured`/`requires_key`/`ProviderCapabilities` (search-by-title, search-by-isbn, cover/ratings/genres), reusing `ladder`'s own key-presence check for `configured` so the two can never disagree about what's usable — it doesn't reorder or gate the ladder itself, just answers "what exists" for a caller that would otherwise have to match on `MetadataProvider`. Backs `GET /api/metadata/providers` (`server/src/backend/metadata.rs`); `carries_genres` is true for all three as of #1659, and `tests/capabilities.rs` cross-checks every flag against what the parsers actually return for a fixture, in both directions. Each provider fills the picker's fields from its own shape (#1659): Google Books `categories` / `pageCount` / the `ISBN_10` `industryIdentifier`, Open Library `subjects` (edition record) or `subject` (search doc) / `number_of_pages`(`_median`) / `identifiers.isbn_10`, and Hardcover — whose **text search goes through its `search` GraphQL endpoint** (`search(query:, query_type: "Book", …) { results }`, a Typesense payload read as `data.search.results.hits[].document`) rather than the `books(where: {title: {_eq: …}})` filter it used to send; `_ilike` is blocked server-side, so that filter matched only a title typed character-for-character and therefore returned **nothing at all** for the "title author" phrase the picker seeds. A search document carries `author_names`/`featured_series`/`genres` where a `books` row carries `contributions`/`book_series`/`cached_tags`, and its `isbns` span every edition of the work, so its candidates carry no ISBN; the `books` shape (reached by ISBN or by `by_ref`) still supplies the `Genre` bucket of the jsonb `cached_tags` plus the representative edition's `pages` / `isbn_10`, and — alone among the three — the series *position* alongside the series name, taken from the same `book_series` row so a name and a number can never come from two different series (#1665). Edition-scoped values are dropped when that representative edition isn't the printing being answered with — on Hardcover's ISBN path the scanned barcode wins, and its most-read edition is usually a different printing. An omitted field is always `None`/empty, never `Some(0)` or `Some("")`, so a provider's "unknown" can't stage over a real value. Hardcover's `cached_tags` bucket names and `editions.pages`/`isbn_10` were verified against the live API (`cached_tags` is `{Tag, Mood, Genre, "Content Warning"}`, each a list of `{tag, count, tagSlug, …}`), and `genre_tags` still reads the blob defensively — it is a jsonb column whose buckets are data, not schema. `search.rs`'s `search_all_providers` (#1657) is the **fan-out** sibling of `climb`: every catalog provider the caller selected asked concurrently (`join_all`, chunked at `FANOUT_CONCURRENCY`) through the same `providers::run` dispatch, answers kept attributed and **un-collapsed** (no dedupe-by-ISBN — two editions of one ISBN from two sources are exactly what the editor's picker exists to show), capped per source at `FANOUT_PROVIDER_LIMIT`, with one `ProviderSearchStatus` row per provider so "no results" reads differently from "not configured" (never requested), "couldn't reach it", and "rate-limited, retry in N" (also never requested — checked *before* the call, since a provider that told us to go away is not made more willing by asking again). Each provider's answer goes through `relevance::filter_and_rank` before it is returned, and the merged list is sorted by that score — which is derived from the candidate and the query alone, never from who answered, so a provider dropping out removes its rows and reorders nothing. It is infallible: a provider failing is its own row, never the search's error. `providers::run` therefore returns `ProviderEdition` (carrying the per-provider `provider_ref` — OL work/edition key, Google volume id, Hardcover book id, falling back to `isbn:<isbn13>`) and `climb` narrows it to `ExternalBookMeta` on the way out, so check-in semantics are untouched. Backs `POST /api/metadata/editions/search`. `hydrate.rs`'s `hydrate_edition` (#1661) is the follow-up call the editor's picker makes once a candidate is selected. **The handle, not the ISBN, is what identifies it**: with an ISBN the provider is asked by ISBN (it names a printing, so it is preferred), and without one — routine now, since a Hardcover search document describes a work — it is asked by `provider_ref` through `providers::by_ref`, each provider shape-checking the handle before addressing it. A malformed ISBN is treated as absent rather than fatal. Plus — for Open Library only — the description from the selected `provider_ref`'s record (`openlibrary::describe`, shape-checked before it is used as a path, so a client-supplied ref can only ever address a record under the configured base) and the existing `enrich` side lookup. Google Books and Hardcover already answer their searches from the record their detail endpoint would serve, so for those two it is the ISBN lookup and nothing more; `Ok(None)` means the provider no longer knows the ISBN, which the caller answers by keeping the row it has. `providers::cover_hosts`/`all_cover_hosts` (#1661) is the catalog's other half: the hosts each provider serves cover bytes from, **including the redirect hops** (`covers.openlibrary.org` → `archive.org` → a rotating `*.archive.org` node), consumed by `server::security_headers`'s `img-src` so a provider added without its cover host can't leave covers silently blocked — and by `cover.rs`'s `provider_cover_image_config` (#1663), the `RemoteImageConfig` the cover-apply fetch runs under (HTTPS-only, that allowlist, `MAX_COVER_REDIRECTS` hops each re-gated). The two consumers are why it is one list: a cover that renders but can't be applied, or the reverse, is the failure a second copy produces silently. `tests/` mirrors the provider split (wiremock), plus `fanout.rs` and `hydrate.rs`; `relevance/`, `throttle/`, and `query/` carry their own sibling test modules.
```

`pages/metadata_edit/metadata_search/` — the edition picker (#1661–#1663) and, since #1665 deleted the "Fetch from Hardcover" panel (one provider, hand-written per-field rows) and dropped that page's "Fetch Summary" button (one field), the metadata-edit page's **only** fetch-from-outside action. Its trigger sits where the latter did, below the description, drawing the same `glyphs::sparkle_glyph` so the two remaining fetch actions — this and Fetch Summary on the book detail page — read as the same kind of thing. Shaped after the check-in flow because it answers the same question ("which of these is your book?") and shouldn't feel like a different app for asking it: a `Stage` machine (`Searching` / `Results` / `Failed` / `Compare`) rendered one screen at a time in a centred card over a scrim. `mod.rs` owns the trigger, the overlay shell, and the handlers; the overlay **searches as it opens** — the query is the book's own title + primary author, read with `peek` so typing in the form doesn't re-render it — so the reader lands on answers rather than on a form. `results.rs` is screen one (query row, candidate rows, per-source footer); `candidates.rs` holds the row and `in_stable_order`, which sorts on `(accounts-for-the-whole-query, title length, title, isbn13, source, provider_ref)` — nothing but the last tiebreak reads *who* answered, so a provider being slow, newly configured, or down removes its rows without reshuffling the rest, and nothing is merged or dropped. The leading key fixes a second problem the provider order caused: for a well-known title the raw list reliably puts four study guides above the novel, so a candidate whose title **and authors** account for every non-stop word of the query leads, shortest title first within that (a title that *is* the book beats one wrapping it in "A Study Guide for …"). Authors are in the haystack because the seeded query is title + author and a book does not repeat its own author in its title; `sources.rs` is the one-line footer whose whole job is that "nothing", "not set up", and "unavailable" read differently; `field.rs` is the field table (#1662) — `MetadataField`, one variant per copyable field with its label, its read on the form signals, its read on `ProviderEdition`, its apply, and `differs`, all exhaustive `match`es so the compiler names every arm a new field still owes; `SeriesIndex` ("Book #") is the arm the retirement added (#1665), since the panel it replaced could set a book number and only Hardcover publishes one; `compare.rs` is screen two, rendering **only the fields the source would change** (typically two or three, against eleven in a full record) with a "show all fields" toggle and take-all. Each row carries one control with two meanings, which is what says which state the row is in: an arrow to take the source's value, and — once the field is carrying an unsaved change — an undo back to the book's own. "Staged" is measured against `orig`, the same frozen baseline the save bar counts against, so it survives a trip back to the results, covers a field edited directly in the form, and can never disagree with the save bar. A staged row therefore stays on screen rather than vanishing the instant it stops differing. `cover_row.rs` is the cover (#1663) — the one field that cannot stage into the form, since `write_override_cover` takes bytes the browser can't fetch cross-origin, so it POSTs `/api/ebooks/{uuid}/cover/from-url`, writes immediately, says so in the row, and bumps the app-wide `CoverCacheBust` so the sidebar preview, the grid, and the detail page pick the new image up without a reload. Applying otherwise **stages** into the page's existing `FormFields` signals — the save bar and `on_save` stay the only writer, so dirty tracking and validation are untouched — and a field the source has no value for cannot be applied at all, because a provider not knowing a field must never blank out a value you already have. Nothing real is shown while the hydrate round trip is in flight: the compare screen renders a placeholder in the table's own shape (`CompareSkeleton`) until the record settles. The search hit it opens with is a partial answer — fewer fields than the provider's own record — so rendering it means rows appearing and rearranging under the reader a moment later, and "take all" would mean a different set of fields depending on network latency. Hidden until `data::list_metadata_providers` reports a usable source, with the overlay's signals inside a component mounted only while open (rule 07). Tags are deliberately not copyable: a provider's subject list lands on `genres` (#1659), while `subjects` is the EPUB's own `<dc:subject>` entries.

```
offline.rs / offline/ — **mobile-only offline-first layer** (`#[cfg(feature = "mobile")]`; web/SSR never compile it). `store.rs`: one SQLite file (`{data_dir}/offline.db`, rusqlite behind a dedicated worker thread fed closures over a tokio unbounded channel — the `token_store` persistence-worker pattern) holding the replica `cache` (key → JSON payload), the mutation `ops` outbox, the `downloads` registry (PRIMARY KEY (book_uuid, format) so dual-format books hold two independent downloads), and `meta` (temp-id counter, last user, last sync). `cache.rs`: `keys::*` builders + `read_through` — the cache-first (stale-while-revalidate) read policy every mobile `data::*` read wrapper goes through: a cache hit returns immediately, rows older than the 30s fresh window revalidate in the background (one in-flight revalidation per key; skipped while offline or while outbox ops are pending), and a byte-changed payload bumps the generation watch channel that `use_cache_generation` (lib.rs) feeds into page fetch effects; a cache miss fetches inline — or fails fast with `DataError::Offline` when known-offline — and HTTP/decode errors never fall back to stale data. `refresh` is the awaitable pull-to-refresh variant: it bypasses the fresh window and lands the result through the same compare-put-notify path (no-op while offline, while ops are pending, or while the key is already revalidating). `read_through_network_first` keeps the old policy (plus an offline fast path) for the two reads where a stale answer would be a correctness bug: `get_me` (the account-switch wipe keys on the fresh identity) and `get_progress` (the cross-device LWW reconcile). `sync.rs`: `NetState` watch channel (online/pending/dropped), `is_offline_error` (excludes reqwest decode errors, includes the fast-fail `DataError::Offline`), `write_through` (try server, else queue), the runtime loop — `/api/_health` probe every 15s while offline, `background_tick` every 60s while online (drain + TTL-gated replica refresh + resume-rail warm) with an extra tick at boot and on reconnect — and the drain — ordered outbox replay with last-write-wins semantics, a stale guard on progress writes (drops a queued position when the server's `updated_at` is newer), 404-on-delete-as-success, 4xx drop + "couldn't sync" counter, halt-and-retry on connectivity/5xx, and a cache-generation bump after resolving ops so open pages re-read. `outbox.rs`/`outbox/apply.rs`: the serde `Op` enum (coalesce keys for idempotent upserts), negative client temp ids for offline-created highlights/bookmarks/shelves/journal entries with structural temp→real remap across queued ops and cached JSON on drain, and the optimistic cache-application helpers. `replica.rs`: background full-library sync (pages `GET /api/ebooks` by cursor; kicked by every online browse and by the sync tick, TTL 300s) + pure offline sort/filter/pagination (`off:{offset}` cursors) and substring search fallback — the known-offline landing/search path serves these directly with zero network. `downloads.rs`/`downloads/engine.rs`/`downloads/staleness.rs`/`downloads/verify.rs`: the Kindle-style download manager — per-uuid dirs under `{data_dir}/downloads/`, streaming fetch to `.part` files with Range resume, manifest/metadata/artwork cache warming, and the in-memory registry (watch-channel generation counter) behind the book-detail rows / landing badges / account Downloads list. Each `PlannedFile` snapshots two validators (rule 09): `http_etag`, the response `ETag`, replayed as `If-Range` so a resume against a replaced file gets the whole new body rather than a spliced 206; and `source_etag`, `BookFileInfo.etag` at download time, which `downloads/staleness.rs`'s `is_stale` compares against a later metadata refresh to drive "Update available" (conservative — a missing validator on either side reports not-stale). `staleness.rs` also holds `refresh_stale_flags`, the TTL-gated (15 min) sweep behind `POST /api/downloads/validators` — one request for the whole device, carrying no metadata and writing no cache rows; per-book metadata fetches on a 60s tick were a request-per-download polling loop — and `redownload`, the chip's action: a single serialized operation that leaves the existing files in place and lets the engine rename over them on success, restoring the prior entry if anything fails, since `remove` + `start` raced the async deletion against the new write and discarded a readable book before knowing the replacement would arrive. `verify.rs` backstops the residual no stat-derived validator can see, to a degree that differs by format: an EPUB is validated by reading every member to EOF, which checks its recorded CRC-32 and so catches even a same-length splice that leaves the archive's structure valid; an M4B/M4A only gets a box-chain walk, which catches truncation and a splice that changes a box size but *not* a same-length one inside `mdat`; raw MP3 has no container and reports Unverifiable. A file reported damaged is deleted rather than promoted to "complete". The `http_etag` is recorded from the response headers rather than the result, so an interrupted transfer's `.part` is still resumable under `If-Range`; and a part whose `source_etag` provably changed is discarded rather than mixed with parts from a different edition of the book. `media.rs` (+`media/revalidate.rs`): the loopback media server — axum on `127.0.0.1:{random port}` guarded by a per-boot random `?token=`, serving downloaded files with single-range 206 support (so `<audio>` can seek) and the `/img` proxy that caches covers/thumbs on disk (fetch-through while online, cache-only offline). Every `/img` response is `private, no-cache` with a content-derived `ETag`, never a `max-age` — the WebView honours a `max-age`, so a day-long one meant a re-render never reached the handler, revalidation never ran, and the one render that did reach it handed back the old bytes with another day of freshness (a cover replaced elsewhere could take two days or a restart to appear). Asking every render is cheap because an unchanged image answers a bodyless 304 over loopback. Each cached image stores the *server's* `ETag` in a `.etag` sibling next to its `.ct`, and an entry older than `IMG_REVALIDATE_AFTER_SECS` (5 min) is revalidated upstream with `If-None-Match` *after* the cached copy has already been served, via `media/revalidate.rs`'s `revalidate_in_background`; a 304 touches the entry's mtime so the window restarts rather than leaving it permanently overdue and re-asked on every render — so a cover edited on another device lands on the next render without the request that noticed it paying a round-trip, and a 304 leaves the bytes untouched. Revalidation is skipped while offline, while an entry has no stored validator (a "revalidation" would be a full refetch), and while one is already in flight for the same path (the `claim_revalidation`/`lock_cache_key` machinery in `revalidate.rs`), so a grid scroll can't become one request per visible cover. Every response carries `Access-Control-Allow-Origin: *` because the WebView origin is wry's custom scheme. `offline::init()` (called from `mobile/src/main.rs` before launch) opens the store, hydrates the download registry and the reader/audio position maps, and starts the server; every piece degrades to online-only behavior when the data dir or SQLite open fails.
```

```
backend/metadata.rs — `GET /api/metadata/providers` (#1983): any authenticated user (no admin gate) reads `db::catalog` over settings-over-env-resolved `db::provider_keys` — the provider capability catalog (identity, `configured`, `requires_key`, per-provider capabilities), carrying no key material. `POST /api/metadata/editions/search` (#1657): `can_edit`-gated like the overrides *write* (it spends outbound provider calls), 400 on a blank/oversized query or an explicitly empty provider list, then always 200 — `db::search_all_providers` reports a failed source on its own status row rather than failing the request. `POST /api/metadata/editions/hydrate` (#2127): the same `can_edit` gate over `db::hydrate_edition`, 400 on a blank/oversized `provider_ref`, **200 `null`** when the provider no longer knows the candidate (a miss the caller absorbs by keeping the list row it has — an error would read as one to discard), and 502 when the provider itself couldn't be reached. logging.rs          — `init_tracing`: layers a compact human-readable stderr sink, a non-blocking daily-rolling JSON file sink (`omnibus.log.YYYY-MM-DD`), and `error_ring_layer::ErrorRingLayer` (#954), all gated by one `RUST_LOG` env-filter. Every other level is a no-op. tests.rs sibling.
metrics.rs          — `layer_and_route`: builds the `axum-prometheus` middleware + `GET /metrics` scrape route (called once at boot; installs the process-global recorder). The admin *write* is the gated `POST /api/settings/registration`; `db::auth::{registration_enabled,set_registration_enabled}` own the `settings` row. It stays out of the auth rate-limiter's allow-list (which is prefix-matched on login/register/logout) because every page mount hits it — pinned by `registration_status_bypasses_the_auth_limiter` in rate_limit.rs. MediaAuthUser gates the image-read endpoints (covers/thumbs/author-photo/suggestion-cover/user-avatar) and additionally accepts the session as a `?token=` query param — the only auth a mobile WebView `<img>` fetch can carry (bearer header + cookie are both absent on those requests)

auth/basic.rs       — `OpdsAuthUser` (#1805): the `/opds/*` extractor — cookie/bearer session first, then `Authorization: Basic` verified via `db::auth::verify_login` (so per-account lockout applies). `BasicAuthState`, layered as an `Extension` by `opds_router`, holds a per-IP `RateLimiter` (credential guessing metered like the login endpoints) and a 60s-TTL SHA-256-keyed verified-credentials cache (one Argon2 per credential per minute, not per request; the user row is re-read on every hit so permission edits still apply). 401s carry a `WWW-Authenticate: Basic` challenge. Confined to `/opds/*` — `/api/*` never accepts Basic. The cache's TTL check and full-cache sweep take an explicit `now` (`cached_user_id_at`/`store_at`, which the production `Instant::now()` wrappers are one line over), so the `basic/tests.rs` sibling exercises expiry and eviction without waiting out a real minute
auth/strategy.rs    — AuthStrategy trait + PasswordStrategy (OIDC/WebAuthn fit the same shape)
auth/boot.rs        — OMNIBUS_INITIAL_ADMIN recovery hook (promotes named user to admin)
```

Mobile auth: bearer-token login flow lives in `frontend/src/data/auth.rs`
under `feature = "mobile"`. `data::mobile_login` / `mobile_register` POST to
`/api/auth/{login,register}` with `client_kind: ios|android|bearer` so the
server returns a bearer token in the JSON body. `data::token_store`
(`frontend/src/data/stores.rs`) keeps the token in a process-local
`OnceLock<RwLock<...>>` and persists it (in every build) to
`<data_dir>/token` with `0o600` perms, where `data_dir`
(`data::app_dirs`) resolves to `Library/Application Support/omnibus` on iOS,
`$HOME/.omnibus` on desktop/dev, and `Context.getFilesDir()` on Android
(resolved via JNI through the ambient `ndk_context::android_context()` that
tao registers). So the user stays signed in across a cold start and is only
logged out when the server rejects the bearer. UI components subscribe to
`data::token_store::subscribe()` (a `tokio::sync::watch` receiver) so a
401-driven `token_store::clear()` reactively redirects to `/login` (the gate
checks the `ServerUrl` context first, redirecting to `/connect` when it's
empty — see the Server URL (mobile) note above). At-rest protection is the
iOS sandbox + Data Protection / Android's per-app UID sandbox + the `0o600`
perms; **TODO**: harden with iOS Keychain / Android Keystore.

```
                      and where that cursor is kept), DeepLink
                      (the `omnibus://book/<uuid>` URLs the widget mints and
                      the app parses back) and OKLCH (the OKLCH↔sRGB
                      conversion for server-provided accents — shared so the
                      widget and the Continue hero cannot draw one book in two
                      different colours)
OmnibusWidgets/     — the WidgetKit extension (`com.omnibus.mobile.widgets`,
                      embedded into the app at `PlugIns/`): ContinueWidget (a
                      `TimelineProvider` that reads the App Group and nothing
                      else, so it renders in Airplane Mode with the app force
                      quit), its three family layouts and the three distinct
                      empty states, ContinueIntents (a widget cannot be swiped,
                      so the medium card shows one book and carries an
                      `AppIntent` that flips to the next — capped at three,
                      and absent from the small card, which answers with
                      whichever book you touched last and nothing else), and
                      WidgetTheme — colours derived entirely from the book's
                      own tone, because the reader's chosen
                      theme lives in the app's `UserDefaults`, which the
                      extension cannot read
```

Both processes address `group.com.omnibus.mobile`, declared in
`omnibus-ios/omnibus.entitlements` and `omnibus-ios/OmnibusWidgets.entitlements`
and named once in code as `WidgetStore.appGroupID`. All three must agree: a
mismatch is silent — the container URL comes back `nil` and every widget falls
back to its placeholder. The app writes the snapshot at each of the four moments
the Home Screen could have gone wrong (`LifecycleSync`'s foreground, background,
background-refresh and book-close hooks), plus on every `bootstrap` exit path —
including the ones that end at the connect or login screen, since a widget
outlives a sign-out and would otherwise keep showing the previous account's
books.

**TestFlight release requires a second provisioning profile.** A profile is
bound to one bundle ID and the app now embeds `com.omnibus.mobile.widgets`,
so `IOS_WIDGETS_PROVISIONING_PROFILE_BASE64` sits alongside
`IOS_PROVISIONING_PROFILE_BASE64` and `ExportOptions.plist` carries a
`provisioningProfiles` entry per embedded bundle. Both App IDs must also carry
the App Groups capability for `group.com.omnibus.mobile` — which means the
*existing* app profile has to be regenerated, not just the new one created: a
profile does not pick up a capability added after it was created.

Getting that wrong fails **silently**, so it is checked from both ends. A
provisioning profile only *permits* an entitlement — the binary has to claim it,
which happens when the target's `.entitlements` is applied at signing time. The
release archive is therefore signed (manual signing, set per-target on the
**Release** configuration and scoped to `iphoneos` so simulator builds need no
distribution credentials); an unsigned archive carries no entitlements at all and
`-exportArchive` re-signs it with only the baseline four, which is how a correct
profile still yields a widget that renders nothing.
`.github/actions/ios-signing/check-profile.sh` asserts each profile's app id, App
Group and distribution type *before* the archive, and the export step re-reads
the signed IPA to confirm the entitlement actually landed. Simulator lanes prove
none of it — they sign ad-hoc.

**TestFlight release:** the manually-triggered
`.github/workflows/testflight.yml` (workflow_dispatch, `macos-26` runner —
Xcode 26 / iOS 26 SDK, which App Store Connect now requires) archives the
Xcode project with manual signing (`xcodebuild archive` +
`-exportArchive`, bundle `com.omnibus.mobile`) and uploads the `.ipa`
with `xcrun altool`, stamping the marketing version from the latest `v*`
release tag so TestFlight tracks the server release. Signing is seven
CI-only repo secrets (distribution cert + password, an App Store
provisioning profile for *each* of the two embedded bundles, App Store
Connect API key + key-id + issuer-id) — enumerated in the
workflow file's header comment. A daily companion workflow
(`testflight-feedback.yml`) turns new TestFlight screenshot feedback into
GitHub issues via `scripts/testflight_feedback_to_issues.py`.

**Why the reader is a WebView.** iOS ships no EPUB renderer, and epub.js already
produces the CFI positions the server's `epub_cfi` / `epub_cfi_range` contract
expects — so replacing it would mean reimplementing pagination *and* CFI
generation compatibly. Assets and book bytes are served over a custom
`omnibus-reader://` scheme so epub.js sees one same-origin space and needs no
cookie. Everything around it — chrome, gestures, sheets, persistence — is
native.

**Comics skip the WebView entirely.** A CBZ is images, so `Comic/` pages them
natively (pinch zoom, paged `TabView`) against the server's per-page endpoint,
or against the downloaded archive via **ZIPFoundation** — the app's only Swift
package dependency, pinned in the project's `Package.resolved`. Positions ride
the same Epub-format progress row as every reader, as a `comic-page:N` anchor
plus the cross-surface percent (`omnibus_shared::comic_page_anchor`), and a
downloaded archive is CRC-verified before it replaces anything on disk.

**Selection is drawn by the app, not by WebKit.** The iOS glue disables
WebKit's own touch selection inside each section (`user-select: none` in the
per-section baseline stylesheet) and runs its own engine instead:
`beginSelectionAt` / `extendSelectionTo` / `beginEdgeDrag` snap a range to word
boundaries and report per-line rects in web-view coordinates, and
`Reader/ReaderSelectionLayer.swift` draws the tint, the handles, and the
`PassageAnchor` the menu hangs off. WebKit's selection is unusable here for two
reasons: its handles and loupe are laid out against a section iframe as wide as
the whole chapter, so in a paginated book they land in the wrong column, and its
long-press recogniser fights the glue's drag-to-turn handler for the same touch.
Highlights stay epub.js marks (they ride the page-turn transform, which a native
overlay would not); their look is one host-document rule, `markStyleCss`, which
switches blend mode with the reading theme.

**The glue is forked.** `omnibus-ios/omnibus/Reader/Web/epub-reader-glue.js` is a
copy of `frontend/assets/vendor/epub-reader-glue.js`, and the two have diverged:
the iOS copy carries `sectionRanges` / `pagesLeftInSection` plus the whole
selection engine above, and the web copy has since moved its pagination onto
`location.start.displayed` and still uses WebKit's own selection. Changing one
does not change the other — check both when touching reader behaviour.

**The page is booted more than once per book.** iOS reclaims the web-content
process of an app that has been in the background a while, and `reader.html` is
loaded again when the reader comes back — announcing `hostReady` a second time
and taking the stage's whole state with it. So nothing a boot reads may be a
snapshot of the open: `ReaderController.restoreCFI` tracks every relocate rather
than holding the CFI `configure` was given (booting the fresh page at the opening
position undid the session's reading, and the relocate that followed persisted
and pushed the revert), and the marks the outgoing page had painted go back on
the pending queue. `webViewWebContentProcessDidTerminate` makes the recovery
explicit, deferring the reload past a backgrounding rather than feeding a fresh
process to the same reclaim.

Typography is the third thing a boot carries, and it is shaped differently from
the other two: it *is* a snapshot, because `bootScript` has to hand the glue one
complete set of options in a single call. So the boot records what it handed over
in `ReaderController.appliedSettings`, and `ready` re-syncs the difference. Both
halves of the reboot window matter and each is carried by a different mechanism —
a change made before the replacement announces `hostReady` rides the boot options
(`bootScript` reads `settings` live), and one made after it announces but before
it paints rides the re-sync. Dropping the second left the settings sheet showing
one size while the page rendered another until the next reboot (#2191). A new
`ReaderSettings` field therefore has to be added in three places, not one:
`bootScript`'s options, `settingsScripts`' diff, and the tolerant decoder.

`appliedSettings` is `nil` whenever no page is holding our typography, and the
two page-death paths each clear only their own half of that — `prepareForReboot`
drops `isReady` and leaves the view, `teardown` drops the view and leaves
`isReady` — so the gate is `hasLivePage`, which asks both, never one alone.

**The models are hand-mirrored, so they drift silently.** `Models/` restates the
`shared/` wire DTOs in Swift with no generator and no compiler tying the two
together, so a field added or renamed on the Rust side surfaces as a runtime 422
(or a `#[serde(other)]`-style fallback swallowing a variant), never a build
error. `omnibusTests/ScanCodecTests.swift` is the pattern for pinning one of
these contracts — assert the encoded keys a handler requires, and that every
enum variant the server can answer with maps to its own case rather than the
catch-all. Worth adding wherever a mismatch would fail quietly.

**Offline writes** follow [rule 08](../.claude/rules/08-offline-writes.md): the
`OpKind` outbox in `Offline/SyncEngine.swift` carries per-user content state
only, never configuration and never commands. `OutboxScope` in `Offline/Cache.swift`
declares each kind's blast radius. `omnibusTests/OfflineSyncTests.swift` covers it,
and `omnibusTests/ReaderSelectionTests.swift` pins the selection payload the glue
posts plus the passage-menu placement rules. CI runs the suite via
`ios-tests.yml` ([rule 01](../.claude/rules/01-dev-environment.md)); to run it
locally:

```bash
xcodebuild test -project omnibus-ios/omnibus.xcodeproj -scheme omnibus \
  -destination 'platform=iOS Simulator,name=iPhone 17' -only-testing:omnibusTests
```
## site/

The marketing site at <https://seamus-sloan.github.io/omnibus/>. Not a crate and
not part of any build — `site/src/` is plain HTML/CSS/JS copied verbatim to the
`gh-pages` branch by [`.github/workflows/pages.yml`](../.github/workflows/pages.yml)
on every push to `main` that touches it.

| Path | Role |
|---|---|
| `src/index.html` | Twelve panels. All copy is real markup, never baked into an image. |
| `src/site.css` | `--pg-*` chrome tokens, dark + sepia directions, and the `body.flow` fallback used below 861x560 and whenever JS is off. |
| `src/app.js` | The panel deck — wheel/key/touch behind one gate, direction toggle, section rail. Progressive: the deck is opt-in, the page reads without it. |
| `src/shots/dark/` | App screenshots, WebP, one directory per colour direction. Stills exported at 2x from the Claude Design "Omnibus" project and re-encoded by [`scripts/site-shots.sh`](../scripts/site-shots.sh) (`… <dir> sepia` writes the sibling set); the PNGs are not committed. |

Because the shots are stills, they are a picture of the *design*, not of what the
server currently renders — they need re-exporting as redesigned surfaces ship
under [#2132](https://github.com/seamus-sloan/omnibus/issues/2132). Only the
dark set exists today and the page references it directly; wiring `app.js` to
swap `src` with the direction toggle is work for whenever a sepia set lands.

Serve it locally with `python3 -m http.server 8000 --directory site/src`. The
deck engages only above 861x560 — below that, and with JS off, `body.flow`
leaves the panels as ordinary stacked sections, so test both.
