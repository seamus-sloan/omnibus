# Architecture

Cargo workspace with six crates:

- **`shared/`** (`omnibus-shared`) — serde types shared across every target (`Settings`, `ValueResponse`, `LibraryContents`, `LibrarySection`). No Dioxus / axum / sqlx deps.
- **`db/`** (`omnibus-db`) — server-side data layer: SQL migrations, SQLite pool init, the normalized query layer, and the indexing pipeline (scanner → ebook metadata extraction → atomic per-library upsert). Consumed by both `server/` (REST handlers) and `frontend/` (server-function bodies). Holds all sqlx / tokio / epub / anyhow dependencies on the server side.
- **`frontend/`** (`omnibus-frontend`) — Dioxus UI + server-function wire layer (`rpc/`, split into per-domain submodules re-exported from `rpc/mod.rs`). Feature-gated:
  - `web` — WASM client build (used by `server/` when `dx serve --platform web` builds it for WASM).
  - `mobile` — Native Dioxus build; uses `reqwest` against `/api/*` REST routes.
  - `server` — SSR/native build; pulls in `omnibus-db` and compiles server-function bodies. Name is hardcoded by the dioxus_fullstack_macro — can't be renamed.
- **`server/`** (`omnibus`) — **unified Dioxus fullstack binary**. Built twice by `dx serve`: once native (feature `server`) for the axum backend + SSR, once WASM (feature `web`) for the hydrated client. Hosts the hand-written `/api/*` REST router for mobile. Depends directly on `omnibus-db`.
- **`mobile/`** (`omnibus-mobile`) — thin Dioxus Native shell that seeds the reactive `ServerUrl` context from `data::server_url_store` and launches `omnibus_frontend::App`. Android-only: nothing builds this crate for iOS anymore — the iOS surface is the native `omnibus-ios/` app below.
- **`mcp/`** (`omnibus-mcp`) — standalone **read-only MCP stdio server**: logs in to any Omnibus instance over `POST /api/auth/login` (bearer session, `--url`/`--username`/`--password` or `OMNIBUS_MCP_*` env vars, transparent re-login on idle expiry) and exposes the library/search/discovery/shelf/stats/progress/annotation reads as MCP tools. Depends only on `omnibus-shared` (with its `schemars` feature, so tool result schemas derive from the wire types) plus `rmcp`/`reqwest`. The write policy lives as `WRITE_ALLOWLIST` in `mcp/src/client.rs`; new tool families are added as `#[tool_router(router = …)]` impl blocks under `mcp/src/tools/` and combined in `OmnibusMcp::new`. The same tool layer is also served **hosted** at `/mcp` (#2314): `server/` depends on this crate's library half (`http` feature → rmcp's streamable-HTTP server transport) and mounts it behind an admin settings toggle, default **off** — see `server/`'s `mcp_http.rs` entry. Connect a client with `claude mcp add --transport http omnibus https://<host>/mcp --header "Authorization: Bearer <api-token>"` (API tokens are the documented credential; session bearers work but idle-expire). The hosted path builds the client with `OmnibusClient::with_bearer` — the caller's token passed through verbatim, no credentials held, a 401 surfacing as `TokenRejected` rather than a re-login.

Default `cargo build` / `clippy` covers `server`, `shared`, `frontend` only. Mobile is excluded via workspace `default-members` because its `mobile` feature is mutually exclusive with `web`; build it explicitly: `cargo build -p omnibus-mobile`. `mcp` is likewise excluded (a client binary daily server work never compiles): `cargo build -p omnibus-mcp`.

**Web request flow (fullstack):** browser → axum serves SSR'd HTML + WASM bundle → hydration → signal effects call Dioxus server functions (`#[get]`/`#[post]` in `frontend/src/rpc/`) at `/api/rpc/*` → same handlers execute server-side against the SQLite pool via an `axum::Extension<SqlitePool>` layer.

**Mobile data flow:** Dioxus signal/effect → `reqwest` call to `/api/*` (hand-written handlers in `server/src/backend.rs`) → signal update → re-render. Mobile deliberately does **not** use the `/api/rpc/*` server functions. Every mobile read is cache-first (stale-while-revalidate): the local copy is served instantly, a background revalidation refreshes it and nudges rendered pages via a generation channel, and known-offline reads never touch the network. User writes queue to a durable outbox on connectivity failure, and a periodic background tick keeps the outbox drained and the library replica fresh — see `frontend/src/offline.rs` below.

**Database:** schema ships as numbered SQL migrations under [db/migrations/](../db/migrations/), embedded via `sqlx::migrate!` and run on pool init in `omnibus_db::init_db`. Applied versions are recorded in the `_sqlx_migrations` table. Add new migrations as `NNNN_description.sql` — never edit an applied file. All tests use `sqlite::memory:` for isolation; the migrator runs against them the same as production.

**Server URL (mobile):** the backend base URL is a reactive `ServerUrl(Signal<String>)` context, seeded at launch from `data::server_url_store` (persisted at `<data_dir>/server` — `Library/Application Support/omnibus/server` on iOS, `$HOME/.omnibus/server` on desktop/dev, `Context.getFilesDir()/server` on Android — plaintext, all builds; the URL isn't secret). Empty on first run → the mobile `ScreenLayout` gate routes to the unguarded `/connect` route (`pages/server_connect.rs`), which validates reachability via `data::check_server` (`GET /api/_health`) before persisting and advancing to `/login`. The login screen shows a connected-to bar with a Back button to change it. `use_server_url()` still returns a `String` snapshot, so all readers are unchanged; `use_server_url_signal()` is the writer accessor.

cleanup.rs          — Library Cleanup detection (#962) plus the transactional apply/undo primitives (#963). Detection: five domain-specific detectors, no writes, all reading the **override-aware** view of the library rather than the raw taxonomy — `MergeEntity::sql` builds the same effective-membership set `browse::list_authors` and `taxonomy::delete_orphan_tags` use (canonical links on books with no override for that field, UNION the memberships an override names), and `fetch_entity_rows` drops entities no book effectively carries, so cleanup never proposes work on an author or tag the reader can no longer see. `detect_authors`/`detect_series`/`detect_tags_merge` share one normalized-key + fuzzy-Jaccard merge shape (`detect_merges`, parameterized by `MergeEntity`); `detect_authors` also flags junk-author rows left behind by third-party import tooling (Calibre/Smashwords artifacts). `detect_tags_split` finds `;`-delimited tag soup (Tier 0) or a long comma-embedded name (Tier 1). `detect_book_titles` strips filename cruft — an author/series/index prefix (Tier 0) or a trailing parenthetical edition note (Tier 1) — behind a literal-character prefilter so only titles that could plausibly match pay for the regex pass, skipping any book that already carries a `$.title` override (the override is the authority on that book's title, whether typed on the edit form or written by accepting an earlier rename). `strip_title_cruft` runs both passes to a fixpoint rather than stopping at the first hit, so a filename carrying an author *and* a series segment loses both and a stacked scene release loses every trailing parenthetical. `detect_all` concatenates every detector's output. metadata_lookup/    — server-side book-metadata resolution for scans that miss the library (F Physical Check-In). Two entry points, one per question a caller can ask: `search_provider_by_isbn` and `search_provider_by_title` — neither names a provider, so callers never learn which are configured. `config.rs` holds `MetadataLookupConfig` (injectable per-provider base URLs) + `ProviderKeys` (resolved settings-over-env by `settings::provider_keys`; a `None` key means that provider is skipped, not failed). `providers/` is one module per provider — `openlibrary.rs`, `googlebooks.rs`, `hardcover.rs` — each implementing the **same trio** (`by_isbn` → `Option<ProviderEdition>`, a text/structured search → `Vec<_>`, and `by_ref` → `Option<_>` for re-fetching one candidate by the handle its search handed out; a clean miss is an empty answer, an `Err` means the provider couldn't be asked), plus `http.rs` (shared client, `strip_url` so a request URL never reaches a log, year trimming, and the two value normalizers every provider shares — `sanitize_genres` and `paired_isbn10`) and `mod.rs` (`run` — the single dispatch — `by_ref`, `run_with_fallbacks`, and `ladder`). **Google's API key travels as an `X-goog-api-key` header, never in a URL** (#2131) — a `reqwest::Error` renders the request URL in its `Display` but never a header, so no fallible step in `googlebooks.rs` has a credential to write into `omnibus.log`, including ones added later; `strip_url` was the guard before that, and being opt-in per call site is exactly how it came to be missing from all three `json()` sites (#2129). **This is the path the leak actually fired on**, and the pairing is why: an unstripped decode error met a sink that walks the cause chain — `{e:#}` at `mod.rs`'s per-rung warn, `search.rs`'s fan-out warn, and `googlebooks.rs`'s swallowed bare-text fallback. A `%e` sink (what `book_summary` has) renders the outer context alone and would have hidden it. `no_google_books_url_carries_the_api_key` asserts the property over every builder rather than trusting each site. Providers are asked in **their own terms**, from a structured `query.rs::SearchQuery { title, author, isbn13 }` rather than one flattened phrase: Open Library gets a fielded `title=`/`author=` pair (handed the concatenation it searches the author's name *inside the title field*, which for "Dune Frank Herbert" returns five books written **about** Dune and not the novel — verified against the live API), Google Books keeps a bare-text `q` (its general search ranks the phrase as well as `intitle:`/`inauthor:` and tolerates typos far better), and an ISBN on the query routes every provider to its exact-identifier lookup. `run_with_fallbacks` widens a query that found nothing — as given, then without the ISBN, then without the author — scoring each rung against *that rung's* query. `relevance.rs` scores and filters what a provider returns (ported from BookOrbit's `candidate-relevance.ts`/`title-match.ts`): NFKD-fold → strip nonspacing marks → lowercase → letters/digits/spacing-marks, then a five-tier title match (exact 10 / whole-word prefix 8 / whole-word containment 7 / token overlap ×6 gated on a **strict** ratio > 0.5 / Levenshtein ×4 gated on similarity **≥** 0.6 — the asymmetry is load-bearing), an author bonus that only applies once the title already scored, an exact-ISBN short-circuit at 100, a floor of 3, a stable descending sort, and a skip-list that **drops** study guides and summaries rather than ranking them lower. Two deliberate divergences from the source, both documented in-module: spacing combining marks are kept (so Devanagari and friends aren't shattered at their vowel signs), and edit distance is counted in `char`s rather than UTF-16 code units. `throttle.rs`'s `ThrottleTracker` remembers a provider's 429 across requests — an escalating per-provider cooldown (Google Books gets its own longer schedule, its quota being daily rather than per-minute), honouring `Retry-After` when sent, reset by a *successful* call — one that recorded no refusal of its own, since a provider client can swallow its own failure and still answer `Ok` — while a lapse only ends the wait and deliberately keeps the escalation level, or the multi-step schedules could never advance past their first step. It lives on `MetadataLookupConfig` rather than the server's `AppState` because the REST handler and the web server function build their configs independently and neither can see the other's router state; `ThrottleTracker::shared()` is the process-wide instance, `fresh()` the isolated one every test uses. `ladder` orders the rungs: the two catalogs first, key-dependent (Google Books leads when keyed, since keyless it shares an anonymous quota it exhausts; Open Library otherwise), then **Hardcover last and only when keyed** — it costs an extra round trip, but it's the one provider carrying a series statement natively. Exactly one rung is **terminal** (the last catalog): if nothing hit and that rung failed, we never got an answer, so its error surfaces as `MetadataLookupError::Provider` rather than a "not found" we can't stand behind; every other rung — Hardcover included — is best-effort. `openlibrary::enrich` is the side lookup that fills `series`/`first_publish_year` (the edition record + the search API's `isbn:` query), joined concurrently with the ISBN ladder so a hit pays no extra latency; it never fails, and callers must hand it a **canonicalized** ISBN since it interpolates into a URL path. Normalization comes from `omnibus_shared::isbn`, shared with the check-in scanner so both ends gate on the same rule. `metadata_lookup/providers/`'s `catalog` (#1983) is the read-only capability catalog alongside the ladder: per-provider identity/`configured`/`requires_key`/`ProviderCapabilities` (search-by-title, search-by-isbn, cover/ratings/genres), reusing `ladder`'s own key-presence check for `configured` so the two can never disagree about what's usable — it doesn't reorder or gate the ladder itself, just answers "what exists" for a caller that would otherwise have to match on `MetadataProvider`. Backs `GET /api/metadata/providers` (`server/src/backend/metadata.rs`); `carries_genres` is true for all three as of #1659, and `tests/capabilities.rs` cross-checks every flag against what the parsers actually return for a fixture, in both directions. Each provider fills the picker's fields from its own shape (#1659): Google Books `categories` / `pageCount` / the `ISBN_10` `industryIdentifier`, Open Library `subjects` (edition record) or `subject` (search doc) / `number_of_pages`(`_median`) / `identifiers.isbn_10`, and Hardcover — whose **text search goes through its `search` GraphQL endpoint** (`search(query:, query_type: "Book", …) { results }`, a Typesense payload read as `data.search.results.hits[].document`) rather than the `books(where: {title: {_eq: …}})` filter it used to send; `_ilike` is blocked server-side, so that filter matched only a title typed character-for-character and therefore returned **nothing at all** for the "title author" phrase the picker seeds. A search document carries `author_names`/`featured_series`/`genres` where a `books` row carries `contributions`/`book_series`/`cached_tags`, and its `isbns` span every edition of the work, so its candidates carry no ISBN; the `books` shape (reached by ISBN or by `by_ref`) still supplies the `Genre` bucket of the jsonb `cached_tags` plus the representative edition's `pages` / `isbn_10`, and — alone among the three — the series *position* alongside the series name, taken from the same `book_series` row so a name and a number can never come from two different series (#1665). Edition-scoped values are dropped when that representative edition isn't the printing being answered with — on Hardcover's ISBN path the scanned barcode wins, and its most-read edition is usually a different printing. An omitted field is always `None`/empty, never `Some(0)` or `Some("")`, so a provider's "unknown" can't stage over a real value. Hardcover's `cached_tags` bucket names and `editions.pages`/`isbn_10` were verified against the live API (`cached_tags` is `{Tag, Mood, Genre, "Content Warning"}`, each a list of `{tag, count, tagSlug, …}`), and `genre_tags` still reads the blob defensively — it is a jsonb column whose buckets are data, not schema. `search.rs`'s `search_all_providers` (#1657) is the **fan-out** sibling of `climb`: every catalog provider the caller selected asked concurrently (`join_all`, chunked at `FANOUT_CONCURRENCY`) through the same `providers::run` dispatch, answers kept attributed and **un-collapsed** (no dedupe-by-ISBN — two editions of one ISBN from two sources are exactly what the editor's picker exists to show), capped per source at `FANOUT_PROVIDER_LIMIT`, with one `ProviderSearchStatus` row per provider so "no results" reads differently from "not configured" (never requested), "couldn't reach it", and "rate-limited, retry in N" (also never requested — checked *before* the call, since a provider that told us to go away is not made more willing by asking again). Each provider's answer goes through `relevance::filter_and_rank` before it is returned, and the merged list is sorted by that score — which is derived from the candidate and the query alone, never from who answered, so a provider dropping out removes its rows and reorders nothing. It is infallible: a provider failing is its own row, never the search's error. `providers::run` therefore returns `ProviderEdition` (carrying the per-provider `provider_ref` — OL work/edition key, Google volume id, Hardcover book id, falling back to `isbn:<isbn13>`) and `climb` narrows it to `ExternalBookMeta` on the way out, so check-in semantics are untouched. Backs `POST /api/metadata/editions/search`. `hydrate.rs`'s `hydrate_edition` (#1661) is the follow-up call the editor's picker makes once a candidate is selected. **The handle, not the ISBN, is what identifies it**: with an ISBN the provider is asked by ISBN (it names a printing, so it is preferred), and without one — routine now, since a Hardcover search document describes a work — it is asked by `provider_ref` through `providers::by_ref`, each provider shape-checking the handle before addressing it. A malformed ISBN is treated as absent rather than fatal. Plus — for Open Library only — the description from the selected `provider_ref`'s record (`openlibrary::describe`, shape-checked before it is used as a path, so a client-supplied ref can only ever address a record under the configured base) and the existing `enrich` side lookup. Google Books and Hardcover already answer their searches from the record their detail endpoint would serve, so for those two it is the ISBN lookup and nothing more; `Ok(None)` means the provider no longer knows the ISBN, which the caller answers by keeping the row it has. `providers::cover_hosts`/`all_cover_hosts` (#1661) is the catalog's other half: the hosts each provider serves cover bytes from, **including the redirect hops** (`covers.openlibrary.org` → `archive.org` → a rotating `*.archive.org` node), consumed by `server::security_headers`'s `img-src` so a provider added without its cover host can't leave covers silently blocked — and by `cover.rs`'s `provider_cover_image_config` (#1663), the `RemoteImageConfig` the cover-apply fetch runs under (HTTPS-only, that allowlist, `MAX_COVER_REDIRECTS` hops each re-gated). The two consumers are why it is one list: a cover that renders but can't be applied, or the reverse, is the failure a second copy produces silently. `cover.rs` also owns `fetch_provider_cover` (#2331), the fetch the cover-apply route actually calls: for every provider but Google Books it is `fetch_remote_image_with` unchanged, but Google's `imageLinks` publishes **only 128px renditions** (`thumbnail` is `zoom=1`, `smallThumbnail` `zoom=5` — the scale is not ordinal), so `googlebooks::upgrade_cover_url` rewrites the same content URL to `zoom=0` (dropping the decorative `edge=curl`) and the two are fetched concurrently. **The upgraded URL cannot be trusted on its status**: for roughly two thirds of volumes Google answers 200 with a substitute rather than 404 — an "image not available" card, a redacted-cover skeleton, or the publisher's colophon in place of the jacket — and neither format nor file size separates them from real art (one skeleton is 246 KB). `is_larger_rendition` judges the bytes instead, keeping the candidate only when it is wider than the thumbnail *and* within `COVER_ASPECT_TOLERANCE` (4%) of the thumbnail's aspect ratio; the thumbnail is always the real cover, so a rendition of it keeps its shape while a substitution does not. Measured over 18 volumes, genuine matches landed within 2.6% and every placeholder missed by ≥5.4%. Anything undecodable, any failure on the upgrade leg, and any non-Google URL all fall back to the thumbnail, so the upgrade can never turn a working apply into a failure. The rewrite is deliberately **not** applied at search time: the picker keeps rendering the cheap thumbnail, and the second fetch is spent once, on the rate-limited apply route, for a cover the reader actually chose. `tests/` mirrors the provider split (wiremock), plus `fanout.rs` and `hydrate.rs`; `relevance/`, `throttle/`, and `query/` carry their own sibling test modules.

The mark is the **current sitting's high-water percent**, not the last position seen: differencing consecutive writes measured the path the reader walked rather than the ground they covered, so flipping back to find a quote and returning charged the stretch in between twice. Forward reading the reader later backtracks out of stays credited — they did read it — which is where a high-water mark and BookOrbit's endpoint-difference session delta part company. It marks rather than differencing `reading_progress.progress_percent` because a CFI-only write (the iOS reader) nulls that column and `spawn_epub_percent_derivation` refills it off the request path, so the live row is NULL half the time — which is also why `state::attach_derived_percent` is a second call site alongside the upsert. A first observation *baselines* (a device syncing a book it is already 60% through has not just read 60% of it) and a move at or below the mark accrues nothing. `stats::sessionize::IDLE_GAP_SECS` of quiet opens a new sitting, and that governs the **mark** alone, never the gain: it is the only thing that lets the mark fall back, which is what keeps a deliberate re-read counting in full where a lifetime high-water would swallow it — but ground beyond the mark is earned on either side of the boundary, since an offline stretch coalesces into one write stamped with the last page turn and so arrives as a single observation long after the previous one. An out-of-order observation (the off-request-path derivation landing late with its position's older event time) extends the sitting rather than opening one, its clock clamped forward so a late arrival can't manufacture a gap; `merge::transaction`'s `clear_sitting_clock` unsets that clock across a merge, because the surviving mark is picked by `updated_at` alone and a 90%-read source winning over a 10%-read target would otherwise ceiling every gain on the merged book for a whole sitting — scoped to the `(reader, format)` pairs holding a mark on *both* books, which is exactly the set the dedupe resolves since it keys on `format` too, and run before it, since afterwards the losing row is gone. The format half carries the common case rather than an edge one: a merge is usually cross-format, so the reader most often holds an epub mark on one book and an audio mark on the other and the dedupe touches neither — clearing a mark the merge never disputed would let it fall on the next observation and hand back ground already counted. Percent is stored rather than pages so a later `print_pages` override retroactively corrects history. Known residual, deliberate: a backtrack spanning a sitting boundary still over-credits, because a per-sitting clamp cannot net across sittings — closing that needs signed deltas or an explicit re-read boundary. `pages_ledger_epoch` reads the cutover day the migration stamped into `settings`. Both tables join `merge::transaction`'s `RETARGET_TABLES` — a per-reader table absent from that list strands its rows on a merged-away uuid — with the marks deduping latest-wins beside `reading_progress` and the day buckets **summed** by `fold_daily_ledger` instead, because a counter loses a whole day's reading to latest-wins; `missing_files`' GC guards on the day buckets too, so a book that still records ground covered is never purged. tests.rs sibling, plus `tests/ledger_path.rs` for the write-path wiring), `resume.rs` (`recent_progress` — the user's newest rows across both formats, ordered by `COALESCE(client_updated_at, updated_at)` — plus `resume_points`, each joined with its book and, for audio, whole-book duration + 1-based chapter number via `hls::resolve_audiobook_file`/`get_parts`/`get_chapters`; ghosted-book rows are skipped, backing the mobile "pick up where you left off" card; a row records the `book_file_id` its position was taken in (migration 0056) so a book carrying two audiobooks resumes in the right one — a soft reference `resume_points` re-resolves against the book, falling back to the first audio file by ordinal, so the Continue CTA's `?file_id=` always names a live file), `session.rs` (`record_session`/`record_session_tx`/`insert_session_tx`). Each `PlannedFile` snapshots two validators (rule 09): `http_etag`, the response `ETag`, replayed as `If-Range` so a resume against a replaced file gets the whole new body rather than a spliced 206; and `source_etag`, `BookFileInfo.etag` at download time, which `downloads/staleness.rs`'s `is_stale` compares against a later metadata refresh to drive "Update available" (conservative — a missing validator on either side reports not-stale). `staleness.rs` also holds `refresh_stale_flags`, the TTL-gated (15 min) sweep behind `POST /api/downloads/validators` — one request for the whole device, carrying no metadata and writing no cache rows; per-book metadata fetches on a 60s tick were a request-per-download polling loop — and `redownload`, the chip's action: a single serialized operation that leaves the existing files in place and lets the engine rename over them on success, restoring the prior entry if anything fails, since `remove` + `start` raced the async deletion against the new write and discarded a readable book before knowing the replacement would arrive. `verify.rs` backstops the residual no stat-derived validator can see, to a degree that differs by format: an EPUB is validated by reading every member to EOF, which checks its recorded CRC-32 and so catches even a same-length splice that leaves the archive's structure valid; an M4B/M4A only gets a box-chain walk, which catches truncation and a splice that changes a box size but *not* a same-length one inside `mdat`; raw MP3 has no container and reports Unverifiable. A file reported damaged is deleted rather than promoted to "complete". The `http_etag` is recorded from the response headers rather than the result, so an interrupted transfer's `.part` is still resumable under `If-Range`; and a part whose `source_etag` provably changed is discarded rather than mixed with parts from a different edition of the book. `media.rs` (+`media/revalidate.rs`): the loopback media server — axum on `127.0.0.1:{random port}` guarded by a per-boot random `?token=`, serving downloaded files with single-range 206 support (so `<audio>` can seek) and the `/img` proxy that caches covers/thumbs on disk (fetch-through while online, cache-only offline). Every `/img` response is `private, no-cache` with a content-derived `ETag`, never a `max-age` — the WebView honours a `max-age`, so a day-long one meant a re-render never reached the handler, revalidation never ran, and the one render that did reach it handed back the old bytes with another day of freshness (a cover replaced elsewhere could take two days or a restart to appear). Asking every render is cheap because an unchanged image answers a bodyless 304 over loopback. Each cached image stores the *server's* `ETag` in a `.etag` sibling next to its `.ct`, and an entry older than `IMG_REVALIDATE_AFTER_SECS` (5 min) is revalidated upstream with `If-None-Match` *after* the cached copy has already been served, via `media/revalidate.rs`'s `revalidate_in_background`; a 304 touches the entry's mtime so the window restarts rather than leaving it permanently overdue and re-asked on every render — so a cover edited on another device lands on the next render without the request that noticed it paying a round-trip, and a 304 leaves the bytes untouched. Revalidation is skipped while offline, while an entry has no stored validator (a "revalidation" would be a full refetch), and while one is already in flight for the same path (the `claim_revalidation`/`lock_cache_key` machinery in `revalidate.rs`), so a grid scroll can't become one request per visible cover. Every response carries `Access-Control-Allow-Origin: *` because the WebView origin is wry's custom scheme. `offline::init()` (called from `mobile/src/main.rs` before launch) opens the store, hydrates the download registry and the reader/audio position maps, and starts the server; every piece degrades to online-only behavior when the data dir or SQLite open fails.

pages/chart_builder/ — the configurable chart builder at `/stats/chart` (#2376, web/SSR-only via `#[cfg(not(feature = "mobile"))]` on the module and a redirect stub on the route). A **standalone surface while `/stats` is being redesigned** rather than a card on it; the intent is for it to become the "customize" escape hatch behind the curated cards, with those cards re-expressed as presets — so nothing links to it yet. `mod.rs` holds the page, the `ChartControls` picker and `ChartCanvas` (which keeps the previous chart on screen while a refetch is in flight, so a picker change never flashes the surface). The page **opens with nothing plotted** and prompts for a measure where the chart will be, so it asks what the reader wants to know rather than handing them an opinion; the fetch effect skips the wire entirely in that state, since the server's answer is already known. Measures are a **checkbox group, not a fixed pair of dropdowns**: the real bound is on the number of y-scales, so any number sharing a unit can be on screen at once and a row greys out only once both scales are claimed by other units — by the same `ChartSpec::can_add` the server validates with, so a control that looks available can never produce a spec the server then rejects. Clearing the last measure is allowed and returns to that opening state, a blocked row is dimmed rather than hidden with a hint beneath saying why, and the split disables itself with its reason rather than offering a selection the server would reject. The bucket/period/split `<select>`s mark the current choice with `selected` on the option — a `value` on a `<select>` does not pick one in server-rendered markup, so without it each renders showing its first entry. `plot.rs` is the generic renderer — a hand-rolled SVG like every other chart in `pages/stats/`, no chart crate — plus `ChartHoverCard`, `ChartLegend` and `ChartTable`. A line **breaks at an absent bucket** rather than bridging it, since an average with no data is unknown and drawing through would assert a value nobody measured, and it is drawn as a **monotone cubic** (`monotone_path`, the interpolation `d3.curveMonotoneX` uses) precisely because that curve *cannot overshoot* — a spline bulging past its own data would draw an average higher than any month recorded. Bars stack when the result says so and otherwise take a lane each; hover is one full-height hit rect per **bucket** rather than per mark, so a reader aiming at a short bar need not hit the bar, and the card then reads every series at once with each value's unit — which is how two series on different scales stay comparable without measuring heights. In a stacked chart a zero slice draws no segment, so the card omits it; unstacked, a zero is the measure's real value and stays. `tween.rs` interpolates between results so a change moves the marks rather than swapping them, and it interpolates **values, never geometry** — every mark's shape derives from the same `values` arrays, so tweening those moves bars, dots, line and area together, where a CSS transition on `y`/`height` would animate the bars while the line's `d` (which CSS cannot interpolate) jumped underneath. Marks are matched **by identity**: a series by measure and slice, a value by its bucket key — regrouping, zooming and toggling all rebuild the arrays, and a positional blend would interpolate March into April. Unmatched marks rise from the baseline, the same motion the CSS entrance plays on a first paint. **Axes snap rather than tween**, deliberately: a lerped maximum drags its tick labels through 3.7 and 7.4, and the ticks are meant to be round. Two gaps against a real transition system, both real: there is **no exit motion** (a departing mark is removed, not shrunk out), and because the scale snaps, a zoom-*in* — which keeps the same keys and values and changes only the scale — has nothing to animate, while zoom-out does. `zoom.rs` is the client-side brush: drag across the plot to narrow to a sub-range, stored as a pair of bucket **keys** rather than indices so a regrouping that replaces the axis drops the zoom instead of framing the wrong stretch, and re-fitted through the shared `fit_axes`. It can only narrow what was already fetched — it never asks for finer buckets, so zooming into three months shows three periods rather than ninety days, and it cannot reach past a `truncated` axis; both need the spec to carry a server-queried window. Entrance motion is a per-bucket staggered rise, and every animation is disabled under `prefers-reduced-motion`. The series palette is the one part of `atrium.css` that does not derive from `--accent`: a categorical scale has to stay distinguishable under colour-vision deficiency and the black theme's accent is achromatic, so six hues are validated as a set against both a light and a dark ground (adjacent-pair CVD ΔE ≥ 8, normal-vision ΔE ≥ 15); three light steps fall below 3:1 on the page, which is why `ChartTable` is an openable table rather than a screen-reader-only one. Everything derives from the prop, so SSR and the first WASM paint match (rule 07). `notes.rs` is the explanation under the chart — **written from the live result, never static copy**: a reader stopped by a greyed-out checkbox wants to know why *that* one is greyed, so every sentence names the units, measures and genres actually on screen. It says what each measure counts (`ChartMeasure::description`, which lives beside `grain`/`unit` so changing a measure's SQL and changing its sentence are one edit), how the scales are laid out — stating outright that a crossing between two independently-sized axes means nothing, the easiest thing to misread here — why the picker has closed off part of its list, what a split does to the marks, and what an empty bucket means (zero for a total, blank for an average). The per-measure coverage caveats and the axis-truncation note fold in under their own heading rather than sitting loose beneath the chart, where they read as a disclaimer nobody asked for. `tests.rs` siblings on all three files; E2E in `ui_tests/playwright/tests/flows/chart_builder.spec.ts`.

backend/conditional.rs (+ conditional/tests.rs) — conditional-request handling for every endpoint that streams bytes off disk (rule 09), reached through `backend::serve_file` / `serve_download`. `open` returns the file handle its validator was derived from — `(inode, mtime secs.nanos, size)` — and `serve` streams from that same handle, so an atomic replace can't land between the stat and the read and serve new bytes under an old validator (the splice the whole mechanism exists to prevent; on Unix a rename can't move an open inode). `evaluate` settles all five preconditions in RFC 9110 §13.2.2 order — `If-Match` → `If-Unmodified-Since` → `If-None-Match` → `If-Modified-Since` → `Range`/`If-Range` — which cannot be split across layers: a stale `If-None-Match` owes the full body even when an `If-Modified-Since` on the same request matches. The admin *write* is the gated `POST /api/settings/registration`; `db::auth::{registration_enabled,set_registration_enabled}` own the `settings` row. It stays out of the auth rate-limiter's allow-list (which is prefix-matched on login/register/logout) because every page mount hits it — pinned by `registration_status_bypasses_the_auth_limiter` in rate_limit.rs. MediaAuthUser gates the image-read endpoints (covers/thumbs/author-photo/suggestion-cover/user-avatar) and additionally accepts the session as a `?token=` query param — the only auth a mobile WebView `<img>` fetch can carry (bearer header + cookie are both absent on those requests)

auth/basic.rs       — `OpdsAuthUser` (#1805): the `/opds/*` extractor — cookie/bearer session first, then `Authorization: Basic` verified via `db::auth::verify_login` (so per-account lockout applies). `BasicAuthState`, layered as an `Extension` by `opds_router`, holds a per-IP `RateLimiter` (credential guessing metered like the login endpoints) and a 60s-TTL SHA-256-keyed verified-credentials cache (one Argon2 per credential per minute, not per request; the user row is re-read on every hit so permission edits still apply). 401s carry a `WWW-Authenticate: Basic` challenge. Confined to `/opds/*` — `/api/*` never accepts Basic. The cache's TTL check and full-cache sweep take an explicit `now` (`cached_user_id_at`/`store_at`, which the production `Instant::now()` wrappers are one line over), so the `basic/tests.rs` sibling exercises expiry and eviction without waiting out a real minute
auth/session_view.rs — the one projection from a `db::auth::Session` onto the wire `SessionView`, shared by the self-service (`auth/handlers.rs`) and admin (`backend/admin_sessions.rs`) listings so the two can't drift on how a client is named. `client_label` names the session's holder: a registered device's own `name` when the session carries a `device_id` (the native clients send `UIDevice.current.name`), otherwise a label derived from the `User-Agent` captured at login (`sessions.user_agent`, migration 0088) — "Firefox on macOS" — falling back to "Unknown client". Ordering is the whole algorithm in both `browser_name` and `os_name`, because these strings impersonate each other: Edge and Opera claim `Chrome`, Chrome claims `Safari`, an iOS header says "like Mac OS X" and an Android one says "Linux". The raw header is never returned to a client — only the derived label. Registered devices are fetched once per listing, not per row. tests.rs sibling.
auth/strategy.rs    — AuthStrategy trait + PasswordStrategy (OIDC/WebAuthn fit the same shape)
mcp_http.rs         — hosted `/mcp` endpoint (#2314): rmcp's `StreamableHttpService` (one shared instance, `LocalSessionManager`) mounted via a hand-rolled `ANY /mcp` handler that (1) reads the admin `mcp_enabled` setting per request — off → 404, so flipping the toggle needs no restart, (2) authenticates the `Authorization: Bearer` through `db::auth::resolve_token` (API tokens and session bearers, same routing as `/api/*`), then (3) scopes the raw token into a `tokio::task_local` around `service.handle(req)` so rmcp's context-less service factory can build the per-caller `OmnibusClient::with_bearer` loopback client against the server's own port (`dioxus::cli_config::server_port()`). Tool calls thus re-enter this same server's REST surface with the caller's token — every permission gate enforced by the handlers, identically to the stdio transport. Host/Origin allowlisting is disabled (bearer-only endpoint; a rebound browser request can't attach the header). tests.rs sibling drives the toggle, auth, and a real initialize→tools/list handshake.
auth/boot.rs        — OMNIBUS_INITIAL_ADMIN recovery hook (promotes named user to admin)

Mobile auth: bearer-token login flow lives in `frontend/src/data/auth.rs`
under `feature = "mobile"`. `data::mobile_login` / `mobile_register` POST to
`/api/auth/{login,register}` with `client_kind: ios|android|bearer` so the
server returns a bearer token in the JSON body. `data::token_store`
(`frontend/src/data/stores.rs`) keeps the token in a process-local
`OnceLock<RwLock<...>>` and persists it (in every build) to
`<data_dir>/token` with `0o600` perms, where `data_dir`
(`data::app_dirs`) resolves to `Library/Application Support/omnibus` on iOS,
`$HOME/.omnibus` on desktop/dev, and `Context.getFilesDir()` on Android
(resolved via JNI through the ambient `ndk_context::android_context()` that
tao registers). So the user stays signed in across a cold start and is only
logged out when the server rejects the bearer. UI components subscribe to
`data::token_store::subscribe()` (a `tokio::sync::watch` receiver) so a
401-driven `token_store::clear()` reactively redirects to `/login` (the gate
checks the `ServerUrl` context first, redirecting to `/connect` when it's
empty — see the Server URL (mobile) note above). At-rest protection is the
iOS sandbox + Data Protection / Android's per-app UID sandbox + the `0o600`
perms; **TODO**: harden with iOS Keychain / Android Keystore.

Both processes address `group.com.omnibus.mobile`, declared in
`omnibus-ios/omnibus.entitlements` and `omnibus-ios/OmnibusWidgets.entitlements`
and named once in code as `WidgetStore.appGroupID`. All three must agree: a
mismatch is silent — the container URL comes back `nil` and every widget falls
back to its placeholder. The app writes the snapshot at each of the four moments
the Home Screen could have gone wrong (`LifecycleSync`'s foreground, background,
background-refresh and book-close hooks), plus on every `bootstrap` exit path —
including the ones that end at the connect or login screen, since a widget
outlives a sign-out and would otherwise keep showing the previous account's
books.

**TestFlight release requires a second provisioning profile.** A profile is
bound to one bundle ID and the app now embeds `com.omnibus.mobile.widgets`,
so `IOS_WIDGETS_PROVISIONING_PROFILE_BASE64` sits alongside
`IOS_PROVISIONING_PROFILE_BASE64` and `ExportOptions.plist` carries a
`provisioningProfiles` entry per embedded bundle. Both App IDs must also carry
the App Groups capability for `group.com.omnibus.mobile` — which means the
*existing* app profile has to be regenerated, not just the new one created: a
profile does not pick up a capability added after it was created.

Getting that wrong fails **silently**, so it is checked from both ends. A
provisioning profile only *permits* an entitlement — the binary has to claim it,
which happens when the target's `.entitlements` is applied at signing time. The
release archive is therefore signed (manual signing, set per-target on the
**Release** configuration and scoped to `iphoneos` so simulator builds need no
distribution credentials); an unsigned archive carries no entitlements at all and
`-exportArchive` re-signs it with only the baseline four, which is how a correct
profile still yields a widget that renders nothing.
`.github/actions/ios-signing/check-profile.sh` asserts each profile's app id, App
Group and distribution type *before* the archive, and the export step re-reads
the signed IPA to confirm the entitlement actually landed. Simulator lanes prove
none of it — they sign ad-hoc.

**TestFlight release:** the manually-triggered
`.github/workflows/testflight.yml` (workflow_dispatch, `macos-26` runner —
Xcode 26 / iOS 26 SDK, which App Store Connect now requires) archives the
Xcode project with manual signing (`xcodebuild archive` +
`-exportArchive`, bundle `com.omnibus.mobile`) and uploads the `.ipa`
with `xcrun altool`, stamping the marketing version from the latest `v*`
release tag so TestFlight tracks the server release. Signing is seven
CI-only repo secrets (distribution cert + password, an App Store
provisioning profile for *each* of the two embedded bundles, App Store
Connect API key + key-id + issuer-id) — enumerated in the
workflow file's header comment.

A third job then **distributes** the build, because uploading it does not:
`altool` delivers the binary and stops, an internal group can be set to
distribute automatically but an external group cannot, and a build nobody adds
to one is invisible to every tester on the public link while the run still
reports success. `scripts/testflight_distribute.py` waits out processing,
submits for Beta App Review when the build still needs it (the first build of a
marketing version does), optionally sets "What to Test", and adds the build to
each group named by the job's `BETA_GROUPS`. It runs on ubuntu — it is pure App
Store Connect API — reuses the same team-scoped API key, and is idempotent, so a
re-run attaches nothing twice. Because that script only ever executes during a
release dispatch against Apple's live API, its suite
(`scripts/tests/testflight-distribute.test.py`, HTTP stubbed, no credentials) is
gated in CI by `script-tests.yml`. Those stubs encode Apple's contract as it
was last observed, and cannot notice it changing: `GET /v1/builds/{id}/betaGroups`
answered for months before App Store Connect began enforcing that relationship
as write-only and returning `FORBIDDEN_ERROR`, and the suite went on passing
against the stub while every real dispatch failed short of attaching anything. Membership is therefore read from
the builds side (`filter[id]` + `filter[betaGroups]`), and a live dispatch stays
the only place the contract is genuinely exercised. A daily companion workflow
(`testflight-feedback.yml`) turns new TestFlight screenshot feedback into
GitHub issues via `scripts/testflight_feedback_to_issues.py`.

**Why the reader is a WebView.** iOS ships no EPUB renderer, and epub.js already
produces the CFI positions the server's `epub_cfi` / `epub_cfi_range` contract
expects — so replacing it would mean reimplementing pagination *and* CFI
generation compatibly. Assets and book bytes are served over a custom
`omnibus-reader://` scheme so epub.js sees one same-origin space and needs no
cookie. Everything around it — chrome, gestures, sheets, persistence — is
native.

**Comics skip the WebView entirely.** A CBZ is images, so `Comic/` pages them
natively (pinch zoom, paged `TabView`) against the server's per-page endpoint,
or against the downloaded archive via **ZIPFoundation** — the app's only Swift
package dependency, pinned in the project's `Package.resolved`. Positions ride
the same Epub-format progress row as every reader, as a `comic-page:N` anchor
plus the cross-surface percent (`omnibus_shared::comic_page_anchor`), and a
downloaded archive is CRC-verified before it replaces anything on disk.

**Selection is drawn by the app, not by WebKit.** The iOS glue disables
WebKit's own touch selection inside each section (`user-select: none` in the
per-section baseline stylesheet) and runs its own engine instead:
`beginSelectionAt` / `extendSelectionTo` / `beginEdgeDrag` snap a range to word
boundaries and report per-line rects in web-view coordinates, and
`Reader/ReaderSelectionLayer.swift` draws the tint, the handles, and the
`PassageAnchor` the menu hangs off. WebKit's selection is unusable here for two
reasons: its handles and loupe are laid out against a section iframe as wide as
the whole chapter, so in a paginated book they land in the wrong column, and its
long-press recogniser fights the glue's drag-to-turn handler for the same touch.
Highlights stay epub.js marks (they ride the page-turn transform, which a native
overlay would not); their look is one host-document rule, `markStyleCss`, which
switches blend mode with the reading theme.

**The glue is forked.** `omnibus-ios/omnibus/Reader/Web/epub-reader-glue.js` is a
copy of `frontend/assets/vendor/epub-reader-glue.js`, and the two have diverged:
the iOS copy carries `sectionRanges` / `pagesLeftInSection` plus the whole
selection engine above, and the web copy has since moved its pagination onto
`location.start.displayed` and still uses WebKit's own selection. Changing one
does not change the other — check both when touching reader behaviour.

**The page is booted more than once per book.** iOS reclaims the web-content
process of an app that has been in the background a while, and `reader.html` is
loaded again when the reader comes back — announcing `hostReady` a second time
and taking the stage's whole state with it. So nothing a boot reads may be a
snapshot of the open: `ReaderController.restoreCFI` tracks every relocate rather
than holding the CFI `configure` was given (booting the fresh page at the opening
position undid the session's reading, and the relocate that followed persisted
and pushed the revert), and the marks the outgoing page had painted go back on
the pending queue. `webViewWebContentProcessDidTerminate` makes the recovery
explicit, deferring the reload past a backgrounding rather than feeding a fresh
process to the same reclaim.

Typography is the third thing a boot carries, and it is shaped differently from
the other two: it *is* a snapshot, because `bootScript` has to hand the glue one
complete set of options in a single call. So the boot records what it handed over
in `ReaderController.appliedSettings`, and `ready` re-syncs the difference. Both
halves of the reboot window matter and each is carried by a different mechanism —
a change made before the replacement announces `hostReady` rides the boot options
(`bootScript` reads `settings` live), and one made after it announces but before
it paints rides the re-sync. Dropping the second left the settings sheet showing
one size while the page rendered another until the next reboot (#2191). A new
`ReaderSettings` field therefore has to be added in three places, not one:
`bootScript`'s options, `settingsScripts`' diff, and the tolerant decoder.

`appliedSettings` is `nil` whenever no page is holding our typography, and the
two page-death paths each clear only their own half of that — `prepareForReboot`
drops `isReady` and leaves the view, `teardown` drops the view and leaves
`isReady` — so the gate is `hasLivePage`, which asks both, never one alone.

**The models are hand-mirrored, so they drift silently.** `Models/` restates the
`shared/` wire DTOs in Swift with no generator and no compiler tying the two
together, so a field added or renamed on the Rust side surfaces as a runtime 422
(or a `#[serde(other)]`-style fallback swallowing a variant), never a build
error. `omnibusTests/ScanCodecTests.swift` is the pattern for pinning one of
these contracts — assert the encoded keys a handler requires, and that every
enum variant the server can answer with maps to its own case rather than the
catch-all. Worth adding wherever a mismatch would fail quietly.

**Simulated offline.** `Offline/DebugOffline.swift` is a DEBUG-only switch that
fails the whole `/api/*` client — and `AuthService.probe`, so nothing quietly
reconnects — with the same `APIError.offline` a real outage produces. It is
flipped by the `--uitest-offline` / `--uitest-online` launch arguments or an
`omnibus://debug/offline?on=…` URL, persisted so a relaunch keeps it, and read
back out of the app's own preferences plist by
[`scripts/explore/ios.sh`](../scripts/explore/ios.sh). It does **not** cover the
background download session. `scripts/ios-release-guard.sh` (`just
ios-release-guard`) asserts it and the other `--uitest-*` hooks are absent from
a Release build; the lane's contract is
[`docs/qa/agentic_exploration/ios_lane.md`](qa/agentic_exploration/ios_lane.md).

**Offline writes** follow [rule 08](../.claude/rules/08-offline-writes.md): the
`OpKind` outbox in `Offline/SyncEngine.swift` carries per-user content state
only, never configuration and never commands. `OutboxScope` in `Offline/Cache.swift`
declares each kind's blast radius. `omnibusTests/OfflineSyncTests.swift` and
`omnibusTests/DebugOfflineTests.swift` cover them,
and `omnibusTests/ReaderSelectionTests.swift` pins the selection payload the glue
posts plus the passage-menu placement rules. CI runs the suite via
`ios-tests.yml` ([rule 01](../.claude/rules/01-dev-environment.md)); to run it
locally:

```bash
xcodebuild test -project omnibus-ios/omnibus.xcodeproj -scheme omnibus \
  -destination 'platform=iOS Simulator,name=iPhone 17' -only-testing:omnibusTests
```
## site/

The marketing site at <https://seamus-sloan.github.io/omnibus/>. Not a crate and
not part of any build — `site/src/` is plain HTML/CSS/JS copied verbatim to the

Because the shots are stills, they are a picture of the *design*, not of what the
server currently renders — they need re-exporting as redesigned surfaces ship
under [#2132](https://github.com/seamus-sloan/omnibus/issues/2132). The markup

from that set (no sepia export yet) keeps its dark render in both directions.

Serve it locally with `python3 -m http.server 8000 --directory site/src`. The
deck engages only above 861x560 — below that, and with JS off, `body.flow`
leaves the panels as ordinary stacked sections, so test both.
