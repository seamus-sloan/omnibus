### High Priority — Progress saves bypass the typed data layer

Both the reader and the audiobook player persist position by hand-rolling a raw `gloo_net` POST with a manually-built JSON envelope instead of calling the typed `data::save_progress(ProgressUpdate)` wrapper that exists for exactly this purpose. `frontend/src/pages/reader/mod.rs:204-216` builds `serde_json::json!({"update":{book_uuid, format, epub_cfi}})` and POSTs it to `/api/rpc/progress`; `frontend/src/pages/listen/helpers.rs:38-50` (`post_audio_progress`) does the same for audio. Meanwhile `data::save_progress` is fully defined for both targets — mobile at `frontend/src/data/progress.rs:18` (POSTs `/api/progress`) and web at `:75` (proxies `rpc_save_progress`) — but a repo-wide grep finds zero callers; only `data::get_progress` is consumed (reader/mod.rs:253). Three concrete consequences follow. (1) The save path is web-only raw HTTP, so the mobile build has no working progress-write path through these pages, blocking F2.1 cross-device sync and the Phase-6 mobile target. (2) The wire envelope is hand-duplicated in two places and can silently drift from `omnibus_shared::ProgressUpdate`, which carries a `validate()` the hand-rolled path skips. (3) Errors are swallowed (`let _ = req.send().await`), so a failed sync write is invisible. There is even a target divergence: the hand-rolled posts hit `/api/rpc/progress` while the typed mobile wrapper hits `/api/progress`. Fix: route both save sites through `data::save_progress(server_url, ProgressUpdate{..})`. That collapses the duplicated envelope into the shared type, gives mobile a real implementation for free, and surfaces a typed `DataError` the page can act on. Cross-device / Kobo / Kindle sync needs the server to be authoritative and the write to be reliable — not fire-and-forget from two divergent POSTs.

### High Priority — Tag-cloud and landing filters lack URL state

Taxonomy filtering lives only in localStorage view-prefs with no URL representation, directly contradicting the F1.8 discovery-pages spec, and the tag cloud's deep-link is a no-op. `docs/roadmap/1-8-discovery-pages.md` states the problem ("Today taxonomy is a filter … leaves no shareable URL") and gives the acceptance criterion: clicking a tag deep-links to `/?tags=fantasy`. But `frontend/src/pages/tag_cloud.rs:111-120` renders every tag as `Link { to: Route::Landing {} }` with no query param — clicking any tag navigates to bare `/` and applies no filter, even though the subtitle says "click to filter" (tag_cloud.rs:59). `Route::Landing {}` (routes.rs:16-17) has no query field. The landing page reads filters exclusively from `view_prefs::load(path)` (landing.rs:123-130) and never inspects the URL, and its search box is driven by the `SearchQuery` context (landing.rs:42), not the URL. So a filtered or searched library view cannot be bookmarked or shared, which blocks the core F1.8 deliverable and the OPDS/sharing direction. Fix: thread filter/search/sort through query params on the landing route (`/?tags=&authors=&sort=`), hydrate `ViewPrefs` from the URL on mount (URL wins over localStorage when a param is present), and make `tag_cloud` build `Route::Landing` with the tag in the query. localStorage remains the no-param fallback.

### High Priority — Async fetch hand-rolled 9x, no use_resource

Every data-driven page reimplements the same async-fetch state machine plus the same loading/error/not-found gate by hand, and Dioxus's `use_resource` (built for exactly this) is used nowhere — `grep use_resource frontend/src` returns zero hits; all fetch sites use `spawn(async move {...})`. Each page declares a `use_signal(|| true)` loading flag plus a `use_signal(|| None::<String>)` error, runs a `use_effect`/`use_reactive!` that spawns the fetch, then writes three early-return blocks: "Loading…", a `p[role=alert]` with a "Back to library" Link, and a not-found guard. This scaffold appears in `author.rs`, `series.rs`, `book_detail.rs`, `tag_cloud.rs`, `authors_index.rs`, `series_index.rs`, `landing.rs`, `search.rs`, and `metadata_edit.rs` (grep confirms 10 files with the loading signal and 9 with "Back to library"). Beyond ~40 lines/page of boilerplate, the hand-rolled version has no cancellation: a stale in-flight fetch can clobber a newer one, which detail pages already paper over with an ad-hoc `still_current` guard (book_detail.rs:95-98). It also forfeits Dioxus suspense / SSR-streaming as more server-rendered discovery pages land (F1.8), and drift is already visible — loading copy is "Loading…" everywhere but "Searching…" on search.rs, and error recovery is a Link on detail pages but bare text on search.rs. Fix: introduce a `use_async_data`-style hook (or adopt `use_resource`) returning a `Loading|Err|Ready` enum plus shared `PageLoading`/`PageError` components, and route the index/detail pages through it. Keyed-by-param resources also delete the manual `use_reactive!` + stale-guard plumbing.

### High Priority — Detail pages refetch /me, defeating CurrentUser

`book_detail.rs` and `author.rs` each fire their own `data::current_user()` round-trip on mount to compute `is_admin`, even though `App` provides an app-wide `CurrentUser` signal context built specifically to eliminate these per-component fetches. `frontend/src/contexts.rs:37-49` documents the rationale verbatim: components gate on `is_admin` by reading one signal "instead of each firing its own current_user() round trip on mount," and "without this every navigation would re-fetch /me from N components and race the /api/auth/* rate-limit budget." `landing.rs:56-62` and `user_menu.rs` read the context correctly. But `author.rs:28-35` and `book_detail.rs:58-65` still `spawn` a fresh `data::current_user().await` (grep confirms these are the only two `current_user().await` call sites in pages). This re-introduces the exact anti-pattern the context removes — extra latency and rate-limit pressure on the two highest-traffic detail pages — and splits auth resolution into two code paths that can disagree: the context distinguishes "unresolved" from "401," while the ad-hoc `if let Ok(Some(user))` collapses transient errors and 401 into non-admin. A comment at book_detail.rs:48-57 reasons about SSR hook-order and `current_user()` stub behavior, suggesting the author intended to keep the direct call, but that still contradicts the context's contract. Fix: replace both local `is_admin` signals + effects with a `use_current_user()` read mirroring landing.rs:58-61 (`is_admin.set(matches!(user_ctx(), Some(Some(ref u)) if u.is_admin))`), dropping the per-page fetch. Mobile keeps its no-admin path.

### Medium Priority — Discovery tiles bypass thumb srcset

This is a duplication finding with a real correctness/perf bug attached. The "cover + title linking to BookDetail" tile is rendered three ways. `landing/grid.rs` has the canonical `GridTile`: it builds the `/api/thumbs/{uuid}/{sm,md,lg}` responsive srcset and passes it to `atrium::Cover` via `src_override`/`srcset` (grid.rs:45-81). `author.rs` re-implements the tile inline twice (series groups + standalone, author.rs:278-312) and `series.rs` renders an `article.series-card` variant (series.rs:124-156) — both calling `Cover { book: book.clone() }` with no `src_override`/`srcset`. The `Cover` docstring is explicit (atrium.rs:115-119): callers must point `src_override` at `/api/thumbs/...` because falling back to the raw `book.cover_url` "would skip the resized WebP cache and break the mobile origin." So the author and series pages serve full-size covers (no WebP, no per-slot resize) on web, and on mobile the un-prefixed `cover_url` points at the wrong origin entirely. Beyond the broken cache, any tile improvement (lazy thumb, keyboard a11y like grid.rs:66-72, the reading-progress badge from the reading roadmap) must be applied 3-4 times and is already inconsistent. Fix: promote a single `BookTile { book, server_url, badge? }` component built on `Cover` that owns the thumb srcset + detail link + title/author line, and route landing grid, author page, and series page through it.

### Medium Priority — Mobile REST transport boilerplate per endpoint

Every mobile-arm data fn repeats the same five-line ritual: `let url = format!(...); let response = with_bearer(http_client().<method>(&url)).send().await?; let status = note_status(response.status()); if !status.is_success() { return Err(drain_error(response, status).await); } Ok(response.json().await?)`. `books.rs` alone repeats this ~8 times, and the block recurs across `authors.rs`, `series.rs`, `tags.rs`, `progress.rs`, `highlights.rs` — grep counts `note_status(response.status())` 27 times and `return Err(drain_error(response, status).await)` 28 times across `data/`. The web arm repeats `crate::rpc::rpc_X().await.map_err(note_server_fn_err)` 31 times. Two functions even duplicate an identical hand-rolled percent-encoder byte-for-byte (books.rs:73-81 and 95-102) — fix one, miss the other. The mobile surface grows substantially in Phase 6, so each new endpoint copies the ritual, and any change to error handling (retry, offline queue, 401→logout) must be applied at dozens of sites. The 401 handling lives in `note_status`; a single forgotten call silently breaks the mobile logout flow for that endpoint. Fix: add generic `mobile_get<T>(url)` / `mobile_get_opt<T>` (404→None) / `mobile_post<T,B>` / `mobile_delete` helpers owning the with_bearer → send → note_status → drain_error → json pipeline, and a web-side `web_call!` wrapper, so each endpoint becomes a path + type; hoist the percent-encoder into one `encode_query(q)`.

### Medium Priority — Three localStorage cache modules duplicate triple

`reader_progress.rs`, `audiobook_progress.rs`, and `view_prefs.rs` are three copies of the same per-key cache-aside pattern with the value type swapped (String / f64 / ViewPrefs). Each defines its own `STORAGE_PREFIX`, an identical `local_storage()` one-liner (`web_sys::window().and_then(|w| w.local_storage().ok().flatten())`), a `storage_key()` formatter, web `load_impl`/`save_impl`, a `#[cfg(mobile)] mod mobile_store` wrapping `OnceLock<RwLock<HashMap<String,V>>>` with get/set/clear, SSR no-op impls, and parallel `tests`/`ssr_tests` modules. `local_storage()` is byte-identical at reader_progress.rs:32, audiobook_progress.rs:51, and view_prefs.rs:34 (grep confirms the defs); the `mobile_store` module is structurally identical across all three. `audiobook_progress` carries a second `_rate` key namespace that doubles its own boilerplate — evidence the copies are already drifting. `view_prefs.rs:4` explicitly notes a "future server endpoint can reuse it"; the roadmap's device-sync phase (F2.1) will add more such caches (shelves, last-position-per-device) and would thread a server write-through into each store separately unless unified. The mobile in-memory map also resets on cold launch (a real resume-position UX bug) and is reimplemented three times, so one fix cannot address all three. Fix: one generic `KeyedStore<T: Serialize + DeserializeOwned>` (or a `kv_store!` macro) parameterized by prefix + value type, yielding load/save with the three platform impls written once; the current modules become thin typed instantiations.

### Medium Priority — Listen overlays duplicate scrim/close shell

The four listen overlays each hand-roll the same frosted-overlay shell instead of sharing a primitive. `chapters_drawer.rs` and `bookmarks_drawer.rs` both open with `div.lp-scrim` (onclick → on_close) → `div.lp-drawer` → `div.lp-drawer-head` (kicker + title + a `btn ghost sm` "Close ↓" button) → `div.lp-drawer-body`; only the body differs (bookmarks_drawer is a 48-line file that is ~90% shell). `speed_panel.rs` and `sleep_panel.rs` likewise render `div.lp-scrim` + `div.lp-panel` + `div.lp-panel-head` (kicker + title). ### Medium Priority — ReadyPlayer models one panel as four booleans

`ReadyPlayer` (listen/ready_player.rs:154-157) declares four independent `use_signal(|| false)` flags — `speed_panel_open`, `sleep_panel_open`, `bookmarks_open`, `chapters_open` — that are mutually exclusive (only one overlay shows at a time). Because exclusivity is not modeled, each of the four toggle handlers manually sets the other three to false: `on_rate` (184-192), `on_sleep` (284-291), `on_bookmark` (293-300), `on_chapters` (302-309) — roughly 12 hand-written `.set(false)` calls implementing radio-button semantics. The four flags are also threaded individually into `ToolbarState`/`TransportState`. This is the classic N-booleans-for-one-choice anti-pattern: error-prone (forget one `.set(false)` and two overlays stack on the shared `.lp-scrim`), verbose, and adding a fifth overlay (the 2-3b listen redesign implies more controls) means editing every existing handler to also close the new one. Fix: replace the four bools with one `use_signal(|| ActivePanel::None)` enum; toggling becomes `set(if cur==X {None} else {X})` and each `_open`/`_active` derives via `==`, making mutual exclusion structural and impossible to get wrong.

### Medium Priority — Reader is 450-line component with inline JS

`BookReadPage` (reader/mod.rs:70-520) is a single ~450-line component, well past the repo's own ~80-line soft cap (.claude/rules/05-rust-style.md). The bulk is one web-gated `use_effect` (lines 164-281) that, in one closure, serializes seven JS literals, constructs three `Closure`s (relocate/status/selection), installs them on `window` via `js_sys::Reflect::set`, spawns an async block fetching server progress, builds a multi-line inline-JS `init` poller string and evals it, then fetches highlights and evals an annotation call per highlight. The relocate callback nests a `spawn_local` that hand-builds a `gloo_net` progress POST (lines 203-216). The contrast is stark with the listen page, which deliberately extracted all interop into `listen/bootstrap.rs` with pure, unit-tested helpers (`resolve_resume_pos`, `parse_file_id_from_url`, etc.) specifically "so the parent stays under the line-count cap" — the reader never got that treatment. Its mount logic is therefore hard to follow, has zero Rust-side unit coverage (e.g. the CFI reconciliation `server_cfi.or(local_saved)` at :262, the reader's equivalent of the listen page's tested `resolve_resume_pos`), and the per-target `#[cfg_attr(not(feature="web"), allow(...))]` noise compounds the clutter. Fix: mirror the listen split — move the mount effect and helpers into a `reader/bootstrap.rs`, extract CFI reconciliation and file-url construction as pure testable fns, and leave `BookReadPage` as chrome + handlers (the good sub-components `ReaderTopChrome`/`ReaderViewerStage`/`ReaderPageTurnButtons` already exist).

### Medium Priority — Reader page numbers regenerated client-side

EPUB page numbers and totals are generated in the browser on every book open via epub.js `book.locations.generate(1024)` (epub-reader-glue.js:174, called inside `book.ready.then` on each `init`), with page/total derived from `book.locations.locationFromCfi(cfi)` / `book.locations.total` (:110-111); the Rust side renders "p. X of Y" from this (reader/mod.rs:43-51 `RelocateData`, :397-406). Locations generation walks the entire spine in JS — the well-known epub.js performance cost — so each visit pays cold-start latency proportional to book size, repeated across devices. Worse for the roadmap: the absolute page index is non-deterministic across devices/viewports, so the "p. X of Y" one device shows cannot be reconciled with another — a problem once F2.x cross-device reading-position sync wants a stable progress metric. The %-complete from CFI (`pct`) is fine to keep client-side, but an absolute page index presented as authoritative should come from a precomputed, server-stored locations manifest. The audiobook side already does this correctly — chapters/offsets come from a server `AudiobookManifest` rather than being computed in the browser. Fix: precompute a locations manifest server-side at index time (or cache the first client generation back to the server) and serve it so the reader hydrates page totals instead of regenerating them.

### Medium Priority — Landing facets ignore truncation cap

The landing page hydrates the entire library and does all sort, filter, and facet-counting in WASM. The roadmap blesses client-side sort/filter for ≤10k books (F1.3), so the in-WASM approach itself is intended — but the implementation silently ignores the server's truncation contract. `landing.rs:137-145` memoizes `facet_counts(&library.read().books)` + `sort_books(apply_filters(...))` over the full hydrated list. The server hard-caps at `MAX_BOOKS_RETURNED` (50k rows) and the `/api/ebooks` + `/api/search` REST handlers expose `X-Total-Count` and (when truncated) `X-Total-Cap` headers so clients can detect truncation (docs/roadmap/1-3-library-views.md). But no frontend code reads those headers (`grep X-Total-Count/X-Total-Cap frontend/src` → zero hits, confirmed). So on a library above the cap, the client sorts/filters a silently truncated set and presents wrong facet counts as authoritative, with no "results truncated" affordance. This is the honest, narrow part of the issue; moving facets/sort into server SQL is a larger, roadmap-deferred change (keyset pagination is the blessed long-term fix) and not required yet. Fix (short-term): read `X-Total-Count`/`X-Total-Cap` and surface a truncation banner so the client-side path is honest about its ceiling; the SQL/keyset migration tracks with F1.3's planned pagination work.

### Low Priority — Reader status diverges between SSR and WASM

`BookReadPage`'s `status` signal (reader/mod.rs:74-83) initializes to `ReaderStatus::Loading` under `feature = web` but `ReaderStatus::Ready` under `not(web)` (SSR/server). The reader route `/read/:uuid` is part of the normal router with no SSR exclusion (routes.rs:24-25, 88-92), so a hard refresh prerenders it. `ReaderViewerStage` renders an `rd-overlay` "Loading…" div when Loading and nothing when Ready (reader/mod.rs:592-604). So SSR emits no overlay while the first WASM hydration paint emits the Loading overlay — prerendered markup and initial client markup differ on a hydration-sensitive subtree. The project's own guidance ("never feature-gate component bodies on web; SSR and WASM must render identical markup") targets exactly this, and the rest of this very file works hard to preserve parity (unconditional hook declarations, comments about keeping hook order identical at :48-52, :73, :85). Whether it produces a visible glitch depends on Dioxus hydration tolerance, but it is a deliberate cfg-divergence in a rendered subtree that contradicts the stated invariant. Fix: initialize `status` to the same value on both targets (always `Loading` — the SSR markup has no live epub.js mount, and the client immediately re-derives it) so prerender and first hydration paint match; the web effect flips it to Ready/Failed after mount.

### Low Priority — Three parallel form-field abstractions

There are three independent labeled-form-field implementations doing essentially the same thing. The auth pages use `components/auth/field.rs::Field` (label + input slot + hint/error/success/action states). The metadata editor uses `pages/metadata_edit/fields.rs::{MeLabel, MeField, MeArea}` (label + input/textarea + edited-badge/locked states, with its own `label_to_id` slug derivation at fields.rs:52). The settings page hand-rolls a third bare `div.settings-field` + `label` + `input` with no shared component at all (settings.rs:102-131). All three solve "render an accessible labeled field with optional state badge," each re-doing the `<label for=...>`/id binding. The divergence is partly justified (auth has error/success visuals; metadata has an EDITED badge), but the core label+input+message scaffold and the for/id binding are duplicated three ways, and settings gets no abstraction at all. As ratings/journaling and admin form surfaces arrive, this fragments further. Fix: a base `FormField { label, input_id, hint?, message?, badge? }` that auth and metadata specialize via props, and route settings through it so its fields stop being bespoke.
